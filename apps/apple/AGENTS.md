# Apple apps (iPhone, iPad, Mac)

Read the root [AGENTS.md](../../AGENTS.md) first: the design gate, copy, tests, security and hygiene rules there apply here. This file adds what is specific to the Apple clients. Their implementation notes and screenshots for the shared spec are in [spec/platforms/apple/](../../spec/platforms/apple/README.md); update them in the same change as any UI change.

## Stack and layout
- One SwiftUI source tree, `apps/apple/JournalApp`, builds the Mac and iOS apps (iPhone and iPad), with AppKit and UIKit text editing. Non-UI code lives in the `apps/apple/Packages/JournalCore` Swift package (document model, Markdown, encryption, local storage, sync, archives, agent access) and must not import UI frameworks. [docs/architecture.md](../../docs/architecture.md) has the code map.
- The Xcode project is generated by XcodeGen from `apps/apple/project.yml` and is not committed. Generate it with `mise exec -- scripts/generate-apple.sh` after cloning and whenever `project.yml` changes; do not edit the generated project by hand.
- The apps are clients only: none includes or starts a server. Each device keeps a complete local library and works offline; sync is optional ([architecture](../../docs/architecture.md)).
- The Mac app runs in the App Sandbox in every build. Bundle identifiers, the keychain access group and the archive file types are frozen: existing installations depend on them. There are two: `org.privatejournal.archive` (`journalarchive`, a package, the folder 1.0 saved; keep it declared and importable) and `org.privatejournal.archive.file` (`journalbackup`, `public.data`, the file 1.1 saves). Add a type beside them if one is ever needed; never retype either ([architecture](../../docs/architecture.md), Compatibility rules).

## Visual and interaction direction
- The app should feel as if Apple developed it: familiar native layouts, controls, menus, shortcuts, and behavior. Do not invent novel navigation or a custom design system when platform conventions work.
- Use a native three-column macOS layout: journals in the collapsible sidebar, entries in the content column, and the editor in the detail column. iPad uses the same split layout in regular width. On compact iOS (iPhone), retain familiar stacked navigation.
- Respect spelling/correction preferences, Reduce Motion, Increase Contrast, Reduce Transparency, Dynamic Type, VoiceOver, Voice Control and Full Keyboard Access, and light and dark appearance.
- Where iPhone, iPad and Mac differ, the difference has a reason and is recorded in the page's "Differences between iPhone, iPad and Mac" section.

## Swift code rules
Details and enforcement are in [docs/engineering/code-hygiene.md](../../docs/engineering/code-hygiene.md); do not duplicate them here.
- Swift API Design Guidelines: descriptive names, one statement per line, small focused operations. No force unwraps or force casts.
- Concurrency: UI on the MainActor, persistence in an actor, immutable Sendable networking, owned and cancellable asynchronous work. Complete strict concurrency checking with warnings as errors; never add an unchecked `Sendable` claim to silence a diagnostic.
- Formatting and lint: the swift-format bundled with the pinned Xcode and SwiftLint in strict mode. Fix findings; never add a blanket suppression.
- Views call the model (`AppModel` and its focused extensions); they do not open the store.

## Toolchain and checks
- Use the Xcode named in [docs/development.md](../../docs/development.md) and the tools pinned by mise (`mise.toml`, `mise.lock`): `mise trust`, `mise install --locked`, and run everything as `mise exec -- ...` from the repository root.
- After edits: `mise exec -- scripts/format.sh`. Then the lanes the change needs, from `scripts/check.sh`: `hygiene` (scripts, workflows, secrets), `apple` (Swift lint, JournalCore tests, Mac tests, iOS simulator build; its parts run alone as `lint`, `core`, `mac` and `ios-build`), `backend` and `audit` when you touch those. [docs/development.md](../../docs/development.md) has the table of lanes and the end-to-end scripts (`test-sync.sh`, `test-native-pairing.sh`, `test-native-accessibility.sh` and others).
- Before a TestFlight build run `mise exec -- scripts/release-check.sh --plan` to see which lanes the change needs, then the check itself; it runs the lanes side by side where safe and can archive both apps. How it chooses lanes, and its limits, are in [docs/engineering/release-checks.md](../../docs/engineering/release-checks.md). Uploading is a separate, protected step ([release operations](../../docs/release-operations.md)).
- Keep resources lean: one simulator lane at a time, no parallel Xcode builds beyond what the scripts do, and clean derived data and test outputs you create. The test scripts use a dedicated test simulator; never change a personal simulator or delete preferences you did not create.
- The test scripts fail on skipped tests; never skip a test to make a lane pass.

## Verifying UI changes
- Follow the design gate in the root file. After implementing, run the app (simulator for iPhone and iPad, the built app for Mac) and inspect the actual UI, resolving every deviation from the reviewed design, before reporting the work done.
- Test like a user: realistic journeys across features on long-lived state, in a Release build where behavior differs, not only isolated cases.
- Refresh the page's screenshots with the capture script, `mise exec -- design/spec-screenshots/capture.sh [iphone] [ipad] [mac]` ([README](../../design/spec-screenshots/README.md); [spec/platforms/README.md](../../spec/platforms/README.md), Screenshots), and capture from the seeded sample library only.

## Signing and releases
- Signing identities, provisioning profiles, team identifiers and App Store credentials never go in the repository. Scripts take the team and identity from the environment or an argument (`JOURNAL_SIGNING_TEAM`, `JOURNAL_SIGNING_IDENTITY`, `scripts/build-mac-development.sh <team-id>`); the project's own signing selection is not committed.
- Unsigned or ad-hoc-signed Mac builds keep keys in the login keychain and can prompt for a password after every rebuild. For daily testing build a copy signed with your own development team using `scripts/build-mac-development.sh`; it uses the data protection keychain, so rebuilds do not prompt ([docs/development.md](../../docs/development.md), Team-signed Mac build).
- Checks that need real signing (`scripts/test-mac-sandbox.sh`) run locally, not in CI; the signing guard in the hygiene lane checks profile and entitlement rules against synthetic fixtures only.
- A public change to the release process, entitlements or the privacy answers also updates [docs/app-store/](../../docs/app-store/README.md).
