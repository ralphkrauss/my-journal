## 1. Fixes without a visible design change

### 1.1 #4 The save-failure alert repeats on every keystroke; closing a Mac window shows two alerts

**Problem.** `flush` (`Model/AppModel.swift:555-568`) sets `error` after every failed write, and a failed write is retried on the next keystroke, so the "Journal" alert returns after each OK while the person keeps typing. [save-failure-retry.md](save-failure-retry.md) says not to repeat announcements on every edit: the persistent "Not Saved" notice (`Views/SaveFailureNotice.swift`) is for what comes after the first alert. On the Mac, closing the window or quitting calls `flush` (`Model/WindowSafety.swift:32-38`, `:130-136`), which sets `error` (the window's alert) and then `presentSaveRecovery()` opens a second, modal alert.

**Fix.** `flush` sets `error` only when saving first fails (`saveFailure` was false) or when the person asked for a retry (Try Again in the alert or in the notice). Later failures while typing leave the notice showing and say nothing more. The Mac close and quit paths flush without announcing, so only the modal alert (“Couldn’t save changes on this Mac.” with Keep Open) appears. No copy changes. Because the alert no longer repeats, the “Not Saved” notice is announced to VoiceOver once, when it first appears (not on every failed write), so a person who can't see it still hears that saving stopped.

**Test.** `DraftSaveTests`: with writes rejected, several edits set the error once; an explicit retry that fails sets it again; success clears `saveFailure`.

### 1.2 #5 Sync Status shows the wrong sentence after the app locks and unlocks

**Problem.** `lockImmediately` (`Model/AppModel.swift:756`) clears `syncError` because a sync problem can name an entry, but keeps `syncHealth`. After unlocking, the toolbar's Sync Status still shows (it follows `syncHealth`), with the fallback sentence "Saved on this device. Waiting to sync." instead of the state's own message. States that stop automatic sync (server reset, access removed, sign-in needed, update needed) don't retry on unlock, so the wrong sentence stays until the person acts or 10 minutes pass (`SyncSchedule.swift`).

**Fix.** Health messages name no entry, so `lockImmediately` clears `syncError` only when there is no `syncHealth`. Nothing is shown while locked either way. No copy changes.

**Test.** `SyncRecoveryTests`: with a stopped state (for example access removed), lock and unlock; the message is still the state's message and its action is still offered.

### 1.3 #7 Delete Journal and Delete Permanently skip Review Changes

**Problem.** [owner-decisions-2026-09-25.md](owner-decisions-2026-09-25.md) §1 says: "if the journal has unresolved changes the alert says “This journal has changes that need review.” with **Review Changes** and **Cancel**", and for Delete Permanently: "failures show the existing error text and, where relevant, **Review Changes**." The journal case also gives `JournalLifecycleError.changed` (the entries changed while the alert was open) the conflict text, which is wrong.

**Fix.**

- **`changed`.** Not a conflict. It shows `JournalLifecycleError.changed`'s own text, “This journal has changed. Review the entries before deleting it.”, in the generic alert with OK, as the other failures do.
- Both alerts close if the app locks, as the existing prompts do. VoiceOver and the keyboard use the standard alert.

**Test.** None for composition. If `DeletionConflictUITests` already has a journal with a conflict, extend it to expect Review Changes; otherwise no new test.

### 1.14 #1 Raw database and system errors reach the person

**Problem.** `error.localizedDescription` is shown as it is on the lock screen (`Views/UnlockView.swift:35`, from `Model/AppModel.swift:369`, `:781` and `Model/AppLockOperations.swift:311`) and in alerts. The database's text can be “SQLite error 11: database disk image is malformed - while executing …” and can include SQL ([sync-health-and-recovery.md](sync-health-and-recovery.md), row 18). Keychain failures read “The operation couldn’t be completed. (OSStatus …)”. The sync path already classifies errors (`SyncHealth.init(classifying:)`); the open, unlock and action paths never did. That classifier also says `DatabaseError` means `localDataUnreadable` for every database error, including a busy or locked database, a full disk and a file that is unavailable while the device is locked. Those are temporary or environmental, and the data is fine.

**Fix.** One classification, used by the open screen (2.1), by sync health and by one function that turns an error into a message. In `Packages/JournalCore`, `LocalDataFailure` classifies an error as:

- **damaged**: a `DatabaseError` whose primary result code is `SQLITE_CORRUPT` (11) or `SQLITE_NOTADB` (26), and `JournalError.invalidData` thrown by the store's own validation. Nothing else is damaged. In particular `SQLITE_BUSY`, `SQLITE_LOCKED`, `SQLITE_CANTOPEN`, `SQLITE_IOERR`, `SQLITE_PERM`, `SQLITE_READONLY`, `SQLITE_AUTH` and file-protection failures are not.
- **needs an update**: `JournalError.newerVersion` and `JournalError.unsupportedFormat` (as `SyncHealth` already treats them alike).
- **full**: `SQLITE_FULL`, `NSFileWriteOutOfSpaceError`, `ENOSPC`.
- **temporary**: every other `DatabaseError`, every Keychain or file-system error, and anything unknown.

`SyncHealth(classifying:)` uses it too: damaged is `localDataUnreadable`; the other database failures are a new case, `localDataUnavailable` (kind `.temporary`, so sync keeps retrying), never `localDataUnreadable`. Its message makes no claim about saving, because the failure is in the local database itself, which is exactly what “saved on this device” would vouch for: “Couldn’t sync right now. My Journal will try again.” The classification decides in 2.1 only what is a newer version; every other open failure shows one screen there.

The message function takes the error and whether the operation was reading or saving (each call site below is one or the other):

| The error is | The message is |
| --- | --- |
| One of the app's own errors (`JournalError`, `JournalLifecycleError`, `PermanentDeletionError`, `JournalNameError`, `JournalMergeError`, `PasswordChangeError`, `ServerConnectionError`, `PairingError` and the like) | Its own text, unchanged. It is already plain. |
| Damaged, reading | “My Journal can’t read your journals on this device. Nothing has been removed. To keep a copy, choose Export Archive in Settings ▸ Backup.” This is also the new text of `SyncHealth.localDataUnreadable`. (The screen in 2.1 has its own text.) |
| Damaged, saving | “My Journal can’t save to your journals on this device. Nothing has been removed. To keep a copy, choose Export Archive in Settings ▸ Backup.” |
| Temporary, reading | “My Journal couldn’t use its data on this device right now. Try again.” |
| Temporary, saving | “My Journal couldn’t save your changes right now. Try again.” |
| Full (`NSFileWriteOutOfSpaceError`, `ENOSPC`, the database's full error) | “There isn’t enough space on this device. Free up space, then try again.” (the wording of the archive export's message, made general) |
| A network error (`URLError`) | The sentence of 1.13, chosen by `SyncHealth`. |
| A Keychain error | “My Journal couldn’t use the device key. Try again.” (“device key” is the term the lock screen already uses.) |
| Anything else | “Something went wrong. Try again.” |

“Hasn’t changed” is not claimed anywhere: opening a library runs its migrations and settings checks before a later step can fail, so the app can truthfully say only that it didn't remove anything.

The system's own text goes to `os_log` as private data (domain and code only, never the description, which can hold SQL or a title). Surfaces that already map their errors (`ArchiveView.showInspectionError`, the connection flow's `show`, `ArchiveExport.message`, `MarkdownExportController.message`, the sync messages) keep their own mapping and use the function for what falls through.

**Surfaces that use the function** (`localizedDescription` today, 51 places):

- **Opening and unlocking:** `Model/AppModel.swift:369` (opening), `:781` (unlocking with the recovery credential), `Model/AppLockOperations.swift:311` (unlocking with the device). These become the screen in 2.1 for the cases it covers.

## 2. Changes that need the design gate

### 2.1 #2 and #3 “Your journals can’t be opened”

This section was rewritten after the first review (section 4), re-reviewed (section 5), simplified at the owner's request, for users and for the code (Windows and Android will rebuild every state, so each state, action and rule has to earn its place), and then confirmed by the review in section 6, whose changes are made below.

**What is wrong today.**

- **A damaged library or one from a newer version leads to a dead end (#2).** `Model/AppModel.swift:339` sets `locked = true` before the library opens. If `JournalStore` throws (a damaged database, or `JournalError.newerVersion` after a downgrade), `locked = appLockOn` at `:362` is never reached, `store` stays nil and the lock screen shows (`Views/RootView.swift:96`): “My Journal Is Locked”, the raw error in red, and “Unlock with ‹Login Password›”. That button returns at once, because `unlockWithDevice()` needs App Lock on (`Model/AppLockOperations.swift:259`) and a store (`storeForUnlock()`, `:182`). No Settings, no Erase, no Import is reachable. The same dead end exists for a library whose device key is missing and whose password or recovery key is forgotten (`load()` throws “Your device key is unavailable…”, which is the normal result of restoring an iPhone from a backup: Keychain items are `…WhenUnlockedThisDeviceOnly`).
- **Damage found while reading never reaches a screen.** `JournalStore.init` (`Packages/JournalCore/Sources/JournalCore/Store.swift:76-122`) touches only settings, a count of records and the migrator; page-level damage in records, history or attachments is found by the first `refresh()` (`viewSnapshot`). Today that leaves a live store, an empty-looking library the person can type into, and an alert with the raw SQLite text.
- **A failed open can leave a store behind.** `openLibrary` (`Model/AppModel.swift:382`) assigns `store` first and then reads the Keychain and decodes the saved connection. If either throws, the library is open but `load()` reports a failure.
- **A missing library folder or database opens as an empty library.** `JournalStore.init` creates the folder and the SQLite file. A restore or cleanup that leaves `configuration.json` naming a folder that is gone gives an empty journal with no message, and sync then uploads emptiness.
- **A configuration file that exists but can't be read looks like a first launch (#3).** A missing file means first launch (`Model/AppModel.swift:330`). A file that exists but fails to read or decode throws at `:331-332`, the catch only sets `error`, `configuration` stays nil, and `Views/RootView.swift:98` shows the welcome screen. Start a Journal, Connect to a Server and Import Archive all end in `persistConfiguration()`, which overwrites the same file (`:448-451`). Nothing names the old library any more, so it is orphaned, and the app's own cleanup then deletes it: `removeAbandonedCopies` (`Model/ServerJoining.swift:308-321`) removes any `vault-` folder the configuration doesn't name once it has been idle for an hour, while its Keychain items stay behind.
- **Switching libraries without a store forgets the old one.** `Model/ServerJoining.swift:268` passes `store == nil ? nil : oldConfiguration` to `librariesSuperseded(by:)`, so a connect with a configuration but no open store records nothing. File ▸ Import Archive… is enabled whenever the app isn't locked (`AppCommands.swift:44`), `onOpenURL` accepts an archive (`Views/RootView.swift:218`), and `installArchive`'s `else` branch (`Model/AppModel.swift:843`) builds a new configuration from nothing: it records nothing as superseded, leaves `connectionKeyID` unset (so the new library falls back to a path-derived connection name that can belong to another library) and drops App Lock.

**Principle.** The app never replaces a file it couldn't read, never switches to another library without recording the one it leaves, never tells the person more than it knows, never turns App Lock off on its own, and Erase Journals and Settings removes everything the app stores, whatever it could or couldn't read.

**What the simplification removed** (each was in the first re-review draft): the separate “damaged” and “not available now” states, Start Over…, kept libraries, the lenient JSON reading of an unreadable settings file and `unidentifiedKeys`, the saved copy of that file and the rule that backs it up, Mac TestFlight detection (and, for one copy of the text, iOS's too), the two-failed-attempts rule (it is one), and authentication-before-the-screen (below). What replaced them is one property of the model, one screen and an Erase that doesn't need to read anything. The confirmation review (section 6) removed five more: the “not connected” case of the Erase alert (the app can't know it), the rule that a failed Keychain listing stops Erase, the Open App Store button, Import's wait behind a failed Try Again, and the failure line's accessibility value.

#### What the model knows

`AppModel.libraryProblem: LibraryProblem?`, nil when there is none, otherwise one of four values. It never reuses `locked`: “locked” keeps meaning “waiting for the person's authentication”, except for `needsKey`, which is the existing lock screen with the credential field.

| Value | When | Shown by |
| --- | --- | --- |
| `settingsUnread` | `configuration.json` exists but doesn't read or decode (a read error and bytes that don't decode are treated alike) | the new screen |
| `cantOpen` | `journal.sqlite` of the library the configuration names is missing; or opening fails for any other reason (the store, the device key's Keychain item, the saved connection that doesn't decode, a wrong-sized key, a crypto error); or the first read of the journals after opening fails (below) | the new screen |
| `newerVersion` | `JournalError.newerVersion` or `JournalError.unsupportedFormat` at any of those steps, including from the recovery format the settings name | the new screen |
| `needsKey` | the library requires a password and its device key item is absent (the existing “Your device key is unavailable” case, now a value instead of a thrown string) | the lock screen, as today |

Only newer version is told apart from the rest. A damaged database, a busy or locked one, a full disk, a Keychain that can't be read and a file that's unavailable while the device is locked all show the same screen with the same buttons: the person's choices are the same, and the app can't reliably tell a permanent fault from a temporary one. `LocalDataFailure` (1.14) still chooses the wording of alerts and sync messages, and decides here only what is a newer version.

**First read.** `openLibrary` sets `firstReadPending`; the first successful `refresh()` clears it. While it is set, a failed `refresh()` is a failed open: the library is closed (below) and the problem is set, whichever caller made it (`load()`, `readJournalsAfterUnlocking` after App Lock, `unlockWithRecovery`). Later failed refreshes keep the alert of 1.14. This is what makes damage inside the records (the commonest real corruption: the store opens, reading fails) reach the screen.

**Closing what failed.** `openLibrary` becomes `async` (closing a store is). It makes the store and connection local values and assigns `store` and `connection` only when everything succeeded; if the Keychain or the connection fails after the store opened, it awaits `close()` first, so Try Again can never overlap an open handle on the same file. A failed first read does the same in one function: it clears `connection`, `store` and `masterKey`, calls `configureSync()` (which stops sync and the agent publisher), awaits the old store's `close()`, sets `locked = false` and `error = nil`. A problem state never has a live store.

**Opening requires the database to exist.** `openLibrary` checks that `journal.sqlite` exists in the library's folder (or in the data folder for an old library) before the store is made. `start`, importing and joining make their library, with its file, before any configuration names it, so only an existing library goes through `openLibrary`. A configuration naming a missing folder is `cantOpen` and nothing is created.

#### Where it appears

A screen of its own, not the lock screen. `RootView` chooses in this order:

1. not loaded: “Opening Journal…” (as today);
2. locked: the lock screen (as today, including `needsKey`, below);
3. a library problem other than `needsKey`: this screen;
4. no library: the welcome screen;
5. the recovery key, then the journals (as today).

**App Lock.** The screen is shown at once, with no authentication, and exposes nothing about the journals or the server: a person who can't unlock learns only that something is wrong. A problem library is never locked (`lockImmediately` returns without locking while `libraryProblem` is set, so inactivity and the background don't put up a lock screen that has no store to unlock). The two actions that remove something, Import Archive… and Erase Journals and Settings…, ask for the device's authentication whenever App Lock is on **or its setting can't be known** (`settingsUnread`), so a stranger can't use them; a device without a passcode goes on, as for every Erase. When Try Again succeeds with App Lock on, `load()` ends locked as at any launch and the lock screen follows. The automatic retry below is the same: if it succeeds while the screen is up, the person lands on the lock screen, never on the journals. This replaces the first draft's authentication-first ordering, which needed a second unlock path without a store and couldn't cover an unreadable settings file anyway.

**Why Erase waits for one failed Try Again, and Import doesn't.** Erase removes the journals, so it is held back until a retry has failed. A restart or a few seconds fixes most causes, and the launch's own failed open is the first failure, so one failed tap is two failures in a row. A way out must exist because some causes are permanent (a connection item that doesn't decode, a Keychain item in a bad state), and an unbounded Try Again would be the dead end this change removes. Import is shown at once because it removes nothing until it has read and checked the archive and the person has confirmed a sheet that says what is lost, so a premature tap loses nothing it didn't say (the confirmation review, section 6). The count is `AppModel.failedRetries`, in memory, and gates only Erase: only a person's tap counts. The automatic retry below, and a tap while the iPhone's protected data isn't available, never count. Relaunching starts again, since a restart is also a fix.

**Automatic retry (iPhone and iPad).** Items are `…WhenUnlockedThisDeviceOnly` and files use the default protection class, so a launch before the first unlock or while the device is locked fails to open for a reason that ends by itself. While `UIApplication.shared.isProtectedDataAvailable` is false the screen offers no Erase or Import whatever the count, and the model runs `load()` again when `protectedDataDidBecomeAvailableNotification` fires. The Mac has no equivalent; Try Again is the retry there.

#### Actions and why each is offered

- **Try Again** (every state but newer version). It runs the opening again from the start (`retryOpening()`: clears the problem and runs `load()`, which re-reads the configuration), and a tap that ends in a problem again counts once.
  - **If it fails**, the screen is the same, so it says so: the line “Still can’t be opened.” stays directly under Try Again until the next attempt starts. It is plain text in reading order, announced once when it appears (a live region); the button carries no accessibility value, because a button that permanently reads “Try Again, still can't be opened” is unusual and the line is already read next. Focus returns to Try Again.
  - **What re-running does.** `load()` first runs four cleanups; each was checked against the code, because an unopenable library must not be touched. `finishEarlierErasures` (`Model/EraseOperations.swift:194`) acts only on `erased-` folders by the list saved in each, and protects what the current library uses (`libraryNames`, below) only when the configuration decodes, so it is skipped while the settings are unread and runs as before otherwise. `retireAppLockPIN`, `removeAbandonedCopies` (`Model/ServerJoining.swift:308`) and `discardUnsentEncryptionCopy` (`Model/EncryptionOperations.swift:269`) run only after a successful decode, need no store, never touch the library's database, key or connection, and do nothing the second time. A switch the server may have made (`contactingServer`) is left alone until the library opens. Nothing in re-running removes, rebuilds or rewrites a library (rule 4).
- **Import Archive…** (`cantOpen`, at once, while protected data is available; also on the missing-key screen). It is the one way back that needs no working library and no server, from a backup the person made. It is kept, rather than leaving only Erase and then the welcome screen's Import, because the archive is read and checked **before** the unopened library is replaced: a bad archive or a wrong password leaves everything as it was, whereas Erase first would have removed it. For the same reason it needs no wait behind a failed Try Again: it is already behind authentication and a sheet that says what is lost. It opens the existing archive flow. `installArchive` now acts on a library that exists but can't be opened, so its `else` branch builds the new configuration from the unopened one, not from nothing:
  - it records the unopened library as superseded with `librariesSuperseded(by:)` (which keeps what earlier switches left to remove and adds this library, so none is orphaned in turn), including the old configuration's unfinished encryption copy;
  - the new library names its own connection item (`connectionKeyID` is set to its account plus “-connection” whenever the configuration is built new, not only when none existed);
  - it keeps `appLock` and `inactivityLockMinutes` from the configuration it replaces, so restoring never turns App Lock off. The same holds for every replacement: connect already copies both (`Model/ServerJoining.swift:266-267`), encryption copies the whole configuration, and a test pins the import;
  - the sheet adds the sentence in the table. It names no host and reads no Keychain item, so it shows nothing a person who couldn't unlock shouldn't see; the guide adds that the device stays in the server's list of devices until it is removed there on another device;
  - with App Lock on, `installArchive` asks for the device's authentication before it commits, once per import.
  - File ▸ Import Archive… and opened archive files follow one property, `canImportArchive`: with a library open, as today; without one, true for no problem, `cantOpen` and `needsKey`, false for `settingsUnread` (importing would overwrite a file the app couldn't read) and `newerVersion` (the data may be fine and replacing it would be the opposite of the fix). `onOpenURL` uses it too.
- **Erase Journals and Settings…** (`cantOpen` and `settingsUnread` after one failed Try Again; immediately on the missing-key screen). It is the only way out for someone whose journals are on a server and who has no archive: erase, then Connect to a Server… and the journals come back ([erase-device-2026-10-04.md](erase-device-2026-10-04.md)). Tapping it asks for the device's authentication when needed (above) and then shows the alert; the alert's Erase doesn't ask again. The connection is read from its own Keychain item, independently of the store, by `connectionKeyID` or the path-derived name, when the configuration decodes. There are two cases, because absence of the item proves nothing (see the copy tables): *a host was read*, or *anything else* (item absent or unreadable, settings unread). When a host was read, Erase signs the device out as the normal Erase does (a best-effort revoke after the commit). Otherwise it can't, and the guide says to remove the device in Devices on another device. How it removes everything is in the next heading.
- **Connect to a Server…** isn't offered. Connecting joins a server by merging the library on this device, and a library that can't be read can't be merged; after Erase it is the first step of the welcome screen anyway.
- **Not offered:** Erase and Import for a newer version (an update opens it), and Import for unreadable settings. The guide tells a person with an archive and unreadable settings to erase first and then import from the welcome screen.

#### Erase works without reading anything

“Erase Journals and Settings” promises that the device is “as if My Journal had just been installed”. Today it removes what the configuration names, so it needs a decodable configuration. It now removes **everything the app stores**, from the app's own container, which needs no configuration at all.

What lives in the container, and what Erase does with each:

| Where | What | Erase |
| --- | --- | --- |
| Data folder (`Application Support/PrivateJournal`) | `configuration.json`; library folders (`vault-*`, `import-*`); an old library's `journal.sqlite*` and `attachments` in the folder itself; staged exports (`export-*.journalarchive`, `markdown-*`); the Mac's legacy `agent-connections`; anything else the app left | The configuration is moved into the new `erased-` folder (the commit, a file move that needs no decoding, which is also how an unreadable file leaves). **Every other entry the app can move is listed by its exact name and moved with it**, whether or not the configuration names it (`LocalErasure.isMovable`). |
| Data folder, kept | `erased-*` (an erase's own folder, finished by itself); `local-server*` (the Mac server of earlier builds, which may hold the only copy of other devices' changes: [client-only-mac-lists-markdown-2026-10-05.md](client-only-mac-lists-markdown-2026-10-05.md) §1.2); hidden files | Never moved, as today (`isMovable`). The Settings footer's sentence about the former server stays. |
| Temporary folder | Export dialog copies | Removed, as today (`ErasureList.temporaryFiles`). |
| Keychain | Every device key, connection and staged-copy item the app made | Removed, by the query below. |
| Preferences | `formatMarkdownAsYouType`, `ReviewRequestUsage` | Removed, as today. The sync time key is removed when the connection goes. |
| Mac app group container | Nothing of its own: the only thing it ever held, `agent-connections`, is removed at every launch (`LocalAgentCleanup`) | No change. |
| System-owned | Window layout and position (`@SceneStorage`, system state) | Not the app's to remove; no journal content. |

The list is still built before the commit, saved in `erasure.json` inside the erased folder and used by exact name, so an interrupted erase is finished at the next launch (`LocalErasure.leftovers`) and nothing is chosen by a name prefix afterwards. The data folder is the app's own: `removeAbandonedCopies` already treats every `vault-` folder in it as the app's. One list-builder serves every Erase, so the normal Erase from Settings now also removes what the configuration didn't name (an abandoned copy under an hour old, a leftover import).

**Two lists, not one.** What the library uses and what Erase removes are different questions, and the code keeps them in two functions:

- `libraryNames(configuration)`: what the current library uses, from the configuration's own names only (today's body of `erasureList`, without the folder scan and without the sweep). `finishEarlierErasures` uses it to protect the current library's folder and Keychain accounts when it finishes an earlier erase. It is never the sweeping list.
- `erasureList(configuration)`: what Erase removes: `libraryNames` plus every movable entry of the data folder plus, when `sweepsKeychain`, the service's accounts.

If the sweeping list were used for protection it would protect everything: with a new library started after a half-finished erase, `protectedNames` would cover the whole folder and `protectedAccounts` every Keychain account, so a leftover that is still there is never moved and the retry of a failed key removal silently does nothing, exactly when it is needed. Protecting too little would delete the new library's key. The test is named below.

**The Keychain query.** Verified in `Packages/JournalCore/Sources/JournalCore/Keychain.swift`: every item the app makes is created by `SystemSecretStore` with the same attributes: class `kSecClassGenericPassword`, service `org.privatejournal.vault` (one constant, `query(_:)`), an account name, the keychain named explicitly with `kSecUseDataProtectionKeychain` (true, which is every iPhone and iPad item and every team-signed Mac build; false only for the Mac login keychain, which a build without the entitlement and the secrets an earlier build left there use), no `kSecAttrAccessGroup` (so the app's own default group applies: `…org.privatejournal.vault` where `keychain-access-groups` is in the entitlements, `JournalMac-Development.entitlements`, else the app identifier), **not** synchronizable (the attribute is never set, so no item is in iCloud Keychain and a query that doesn't ask for synchronizable items never matches one), accessible `WhenUnlockedThisDeviceOnly`. Every account the app writes lives in that one service: `master-…` (device keys), `…-connection`, `master-…-vault-…` and the staged ones, and the legacy `agent-…`. Nothing else in the app uses `SecItem`.

Erase therefore lists the service instead of naming accounts: a new `Keychain.accounts()` runs `SecItemCopyMatching` with that class, that service and that keychain flag, `kSecReturnAttributes` and `kSecMatchLimitAll`, and never `kSecReturnData`, so no secret is read and nothing prompts. (`SecretStore` gets `accounts()`: the system store lists, the memory store lists its keys, and **the migrating store lists the data protection store only**.) The accounts it returns go into `ErasureList.accounts` with the configuration's names, and are removed one by one through `Keychain.remove(account)`, which already names the keychain and removes from both. Login-keychain items (left by an unprovisioned Mac build, none released) are therefore removed by name only and never listed: listing that keychain can raise an unlock prompt and, on the Mac, shows other builds' items. A data protection listing without the entitlement reports “nothing found” or `errSecMissingEntitlement`; both are treated as an empty list and logged, which is accepted because no such build was released, and a listing failure is not fatal anyway (below). No wildcard delete is ever issued, so the retry mechanism (three launches) and the “never remove an account the current configuration names” rule work as before. Because the data protection keychain only exposes the app's own access groups, and the service name is the app's, another app's items can't match; on iOS the app has no `keychain-access-groups` entitlement, so only its own app-ID group is visible.

The service is shared by every Mac build signed by the team (`archive-mac.sh` signs the shipping build with `JournalMac-Development.entitlements`, so the shipping app, every development build and every re-signed preview or audit copy share one access group and the service name). Hence two rules:

- **The sweep is limited to the app's own data folder.** `sweepsKeychain` is true only for the app's default data folder and not under test: a UI test (`JOURNAL_UI_TEST_ID`, `JOURNAL_DATA_DIR`) and unit tests (which use the memory store) keep removing only the accounts their configuration names, so erasing in one never removes the keys of a person's real library on the same Mac. The model takes this as a property so a test can turn it on with the memory store. There is no bundle-identifier check: a hard-coded copy of the string in `project.yml` would drift, and on iOS another bundle identifier has its own group and can't see these items; on the Mac the next rule does the work.
- **On the Mac only, the sweep keeps accounts that start with this data folder's `keyAccount` (`master-<SHA-256 of the folder>`),** which every account of this folder's libraries carries (`-connection`, `-vault-…`, `-connection-<uuid>`, staged copies), plus the legacy `agent-…` ones. A preview or development copy has another container, so another hash, and its items are not touched by the shipping app's Erase. **Not on iOS:** the container path, and so the hash, changes after a reinstall or a restore, and the Keychain survives deleting the app, so the orphans of earlier installs are exactly what the sweep exists to remove. The platform difference is deliberate; a port rebuilds the rule for its own keystore.

**A failed listing is not fatal.** If the Keychain can't be listed, Erase logs it (domain and code only), commits with the names it can derive (the path-derived `keyAccount` and `keyAccount-connection`, which need no configuration, plus the configuration's names when it reads), erases everything else and shows the normal result. A Keychain that can't be listed usually can't be removed from either; the files go anyway, and a device key without its ciphertext is inert; what can remain is a connection token, which the guide already tells the person to revoke in Devices on another device. This replaces the earlier fail-closed rule, which left a person with unreadable settings and an unlistable Keychain no exit at all (on iPhone the Keychain items survive deleting the app, and the next install couldn't clean them because the sweep is part of Erase). The alert doesn't mention it; the guide does.

What this couldn't verify, to be checked before shipping, on a real iPhone and a team-signed Mac (the unit tests run on the memory store, never the system Keychain): that `kSecMatchLimitAll` attribute listing works for `WhenUnlockedThisDeviceOnly` items while the device is unlocked and fails cleanly while it is locked (Erase asks for authentication, so it is unlocked in practice); that the items of the Mac App Store build are in the group the entitlements `archive-mac.sh` embeds (`JournalMac-Development.entitlements`), which reading the script and `codesign -d --entitlements` on the signed binary settles for the archive path; that the hash prefix on the Mac matches the accounts a real library writes; and a count of items before and after (a one-off public `os_log` line) for a library with a connection and a joined server copy.

**Sign-out.** Only a readable configuration names the connection. An unreadable one leaves it unknown, the alert says so, and the guide says to remove the device on another device.

**Afterwards.** `clearErasedLibrary()` also clears `libraryProblem`, `failedRetries` and `firstReadPending`, so the welcome screen isn't followed by the problem screen.

#### Rules that protect data

1. **Nothing replaces a file the app couldn't read, or abandons a library it couldn't open.** One model-level guard, not menu enablement: while `libraryProblem` is set, `start`, `initializeServer`, `recoverServer`, `installPairedVault`, `installServerVault` (the connect and pairing entry points, setup links included) and `installArchive` refuse, except that `installArchive` accepts `cantOpen` and `needsKey`. Settings shows the one line of the copy table in place of its controls (`SettingsView` gates on `locked` only today). Menu items, buttons and `onOpenURL` are presentation over the guard. **A single backstop sits at `persistConfiguration()`**, which every overwrite of the configuration goes through (about 25 callers, and `start` assigns a fresh configuration and then persists, which is the overwrite this rule fears): while `libraryProblem` is set it throws, except for the archive install that is allowed to switch (`cantOpen`, `needsKey`). The seven refusals above then exist only to fail early with good copy, and a future entry point can't reintroduce the bug. A late failure leaves staged copies behind, which `removeAbandonedCopies` already handles. Other writers were checked and are safe: App Lock and inactivity settings and journal navigation need a store or Settings, which are gated; `rememberKeyAccount` runs only after a decode; Erase sets `configuration = nil` (`clearErasedLibrary`) rather than persisting. Unlocking with the credential from `needsKey` has to keep working, so a test pins it.
2. **Every switch records the library it leaves.** `Model/ServerJoining.swift:268` passes `oldConfiguration` whenever a configuration exists, not only when a store is open (a one-line change, unreachable under rule 1, kept so the two can't drift apart); `installArchive`'s `else` branch builds from the unopened configuration (above).
3. **App Lock is never dropped.** Every replacement carries `appLock` and `inactivityLockMinutes` from the configuration it replaces. The Erase path removes App Lock with everything else and says it erases settings.
4. **Opening never repairs.** A damaged database is left exactly as it is; Try Again and every launch only re-read.
5. **Unreadable settings leave only by Erase.** Erase moves the unreadable file into the erased folder with everything else; nothing else touches it, and no path overwrites it.
6. **Nothing is removed unless the person chose it.** Import and Erase ask, Erase behind a failed Try Again, both behind authentication where it applies and an alert or sheet that says what is lost (Import verifies the archive before replacing anything). Nothing runs automatically except re-reading.

#### Tests

- **First read.** A database that opens but whose records pages are garbage (the commonest real corruption) gives `cantOpen`, with App Lock off and on: no live store, `error` is nil, no raw error text anywhere, the file unchanged.
- **Open failures.** A connection item that doesn't decode, and a configuration naming a folder or database that doesn't exist, give `cantOpen` with no live store and nothing created. A database from a newer version, and a store that throws `unsupportedFormat`, give `newerVersion` and import is refused.
- **Unreadable settings.** A temporary data folder with a `configuration.json` that doesn't decode: after `load()` and after Try Again the state is `settingsUnread` and the file is byte for byte unchanged, `start`, `connect` and `installArchive` refuse, and `finishEarlierErasures` didn't run. A read error is the same state (`MissingDeviceKeyTests` and `DeviceKeyAccountTests` show how these use real folders).
- **Try Again.** Only a tap counts; a success clears the problem; with App Lock on it ends locked. The automatic protected-data retry with App Lock on also ends locked, not on the journals.
- **Erase sweep.** A data folder with a library folder the configuration doesn't name, an `import-` folder, a staged export and an unreadable `configuration.json`, plus a former-server file, and memory-store accounts the configuration doesn't name: after Erase everything is gone except the former-server file; with `sweepsKeychain` off only the named accounts go. On the Mac, an account with a different folder hash is not swept, and one with this folder's prefix is. A listing that throws, with unreadable settings, still commits: the files move, the derivable names are removed and no “Couldn’t Erase” appears (`EraseLibraryTests`, with an injected listing; this replaces the fail-closed test).
- **Half-finished erase, then a new library.** An erase left half finished (a leftover folder and a failed key removal in a saved list), a new library started, then a launch: the new library's folder and key survive and the old leftover is finished. The sweeping list is never used as protection (`EraseLibraryTests`).
- **Erase alert, server sentence.** With the connection item absent after a restore (the `needsKey` setup), the alert contains the “If this device syncs with a server” sentence and never “will be lost” or “isn't connected”; with a host read, it names the host.
- **Backstop.** `persistConfiguration()` called directly while `settingsUnread` and while `cantOpen` (and `newerVersion`) throws, except from the archive install, and the configuration file is byte for byte unchanged. Unlocking with the credential from `needsKey` still works.
- **Import over an unopened library.** The unopened library is superseded, earlier superseded libraries are carried, the new library names its own connection item, App Lock stays on, and the old library is removed after the restored library opens (`SupersededLibraryTests`).
- **App Lock and problems.** A problem state is never locked (inactivity and background); Import and Erase ask for authentication when App Lock is on or the settings are unread, and a cancelled prompt changes nothing (`AppLockTests`, `DeviceOwnerTestSupport`).
- **Missing device key.** Erase and Import are offered and work, in the `MissingDeviceKeyTests` setup.
- **Sync health.** A busy database isn't “can't read” and its message has no “saved” claim (1.14's test).

### 2.2 #13b Agent access: Selected Journals with none chosen

**Today.** In an agent's detail, switching the Journals choice from All Journals to Selected Journals shows every journal switched off. `commit` (`Views/ServerAgentsView.swift:717`) returns when `scope` is selected and nothing is chosen (`selection.isEmpty`), so nothing is saved and nothing is said. The agent keeps reading all journals while the screen reads as if it reads none ([agent-access-simplified.md](agent-access-simplified.md) §7.1 says switching to Selected Journals narrows access at once). The approval sheet avoids the case: Allow is dimmed until a journal is chosen (`canAllow`), but it doesn't say why.

**Decision.** The detail keeps what the person chose and tells them, rather than changing the choice for them. This is a privacy-relevant mismatch (the control reads as narrower than the access), so the message is not footer text, which people skip.

- **Agent detail** (`AgentJournalsSection` with `keepsOne`). While Selected Journals is chosen and `selection.isEmpty`, the first row of the journals list is a notice: the `exclamationmark.triangle` symbol with “Choose a journal. Until you do, ‹Name› can still read all journals.”, in the normal text size and colour, not secondary and not the footer. The footer stays the usual one (“‹Name› can search and read entries in these journals but can’t change anything. It may send what it reads to its AI provider.”). When a journal is switched on, the row goes and the choice is saved after the usual 0.5 seconds. Nothing is saved before, so leaving the detail leaves the agent as it was, and reopening it shows All Journals again because it reads the server's state.
- **The condition is the save condition.** The row shows when `selection.isEmpty`, the same test `commit` uses, not “no journal on this device is on”. The list also shows journals that aren't on this device (they stay in `selection`); if the selection holds only those, `commit` saves it and the agent then reads only journals this device can't see, so the notice must not claim it reads all. The approval sheet keeps the intersection with this device's journals for its Allow button (`canAllow` already does).
- **Approval sheet** (`AllowAgentView`). While Selected Journals is chosen and none of this device's journals is switched on, the same row in the same place says: “Choose a journal to allow ‹Name›.” This explains the dimmed Allow button and changes nothing else.
- **VoiceOver.** When the choice becomes Selected Journals with none chosen, the sentence is announced (`announceForAccessibility`), and the row is read with the list. It isn't colour only: the symbol and the words carry it.
- **Keyboard and Mac.** The radio group and the switches behave as today. Nothing new to reach.
- **iPhone and iPad.** Same row at the top of the list.
- Leaving the detail drops the unsaved choice without a word. That is accepted: reopening shows the true state, and the row was the mitigation while it was on screen.

**Why not the alternatives.**

- *Switch the choice back to All Journals after the delay.* It moves a control the person just moved, and flips between two privacy states without their input.
- *Switch on every journal when Selected is chosen.* It saves a change the person didn't ask for (it ends access to journals created later), and the approval sheet deliberately preselects nothing. It also takes many taps to choose one journal out of several.
- *Do nothing visible* is what is wrong today.
- *Footer text only.* Too quiet for a mismatch that is about access.

**Test.** None: the sentence is view composition, and what is saved doesn't change.

### 2.3 #14 Return on an empty quote line leaves the quote

**Today.** Return in an empty list item leaves the list, but `newlineAction` (`Editor/RichText.swift:621`) excludes quotes (`kind != "quote"`), so Return in an empty quote line adds another empty quote line, and a quote can only be left with Backspace or the Format menu. [list-markers-2026-10-03.md](list-markers-2026-10-03.md) §10 lists this as unchanged behavior ("Return in an empty quote line doesn't leave the quote"), not as a decision. Apple Notes leaves the quote on a second Return, as it leaves a list, and [list-indentation-2026-10-04.md](list-indentation-2026-10-04.md) says leaving a list "stays as in Notes".

**Behavior.**

- Return in an empty quote line, with the caret and no selection, leaves the quote one level at a time, as Backspace at the start of the line does (`ItemFormattingRemoval.removingOneLevel`, `Editor/HiddenMarkers.swift`):
  - a quote line at the top level becomes an empty plain paragraph at the same place; the caret stays on it and no new line is added;
  - a line in a quote inside a quote becomes a line of the outer quote;
  - a quote inside a list item becomes that item's text;
  - on the last line of the text the line break that belonged to the quote goes with it, so the line is the text's empty last line again, as for lists (`endsWithOwnEnd`, `Editor/ListEditing.swift`).
- **In the middle of a quote.** Every line of a quote is its own block, so an empty quote line between two lines of text leaves the quote and the quote splits in two, with a plain empty line between them, as Backspace at the start of that line does today. The lines above and below stay quote lines.
- **Composition (IME).** Return during marked text (Japanese, Chinese or Korean input, dictation in progress) confirms the composition and never runs this path. Both platforms already guard `newlineAction` with this check (`!view.hasMarkedText()` in `NativeEditor.swift` on the Mac, `textView.markedTextRange == nil` on iPhone and iPad); the change keeps it, and the quote branch is only reached after it.
- Return in a quote line with text still continues the quote, and Return at the start of a line with text still puts an empty quote line above it. Return with a selection is unchanged.
- **A known limit.** A quote can't contain a blank line, because Return on an empty line leaves the quote. The workaround is the one Notes has: Return at the start of a line of text puts an empty quote line above it.
- One Return is one undo step, restoring the empty quote line. Edit ▸ Undo reads the system's “Undo Typing”, as for leaving a list today: the newline path passes no action name, and “Undo Paragraph” or “Undo Block Quote” would name a change the person didn't think they made.
- VoiceOver: no announcement, the same as leaving a list today. The block change is visible in the drawn bar; if the owner wants lists and quotes announced, that is one change for both.
- The same on the Mac and on iPhone and iPad, with the hardware or software Return key.

**Code.** `newlineAction` lets quotes into the empty-line branch, and `leavingItem` (`Editor/ListEditing.swift`) handles the `quote` kind by applying the one-level removal that Backspace uses, so the two can't disagree. No copy changes.

**Docs.** The line in list-markers-2026-10-03.md §10 gets a note that build 18 changed it; the owner's request is the source.

**Test.** `ListItemEditingTests`: Return on an empty top-level quote line; on a nested quote line; on a quote inside a list item; on the last line of the text; in the middle of a quote (two quotes with a plain line between); not while text is being composed; and the undo.

### 2.4 #15 Editing and removing an existing link

**Today.** The link sheet only adds a link: its title is a fixed “Add Link” and its address always starts empty (`Views/LinkEditorView.swift`); the text comes from the selection (`Editor/RichText.swift:206-209`). There is no command to edit or remove a link. Typing a new address over the same text happens to work as an edit; removing a link has no route except View Source. [testing-feedback-revision.md](testing-feedback-revision.md) records the sheet as add-only, so this is a functionality change for the owner, who asked for it.

**Behavior.**

*Which link the commands act on.* The link at the caret, or the link the selection is in. A caret in a link, or at either end of one, counts (the character before the caret first, then the one after). A selection counts when it lies inside one link. A selection that runs across more than one link, or partly outside one, has no single link to edit: it offers Add Link… as today, and Remove Link takes away every link it touches, whole (a selection covering only part of a link removes the whole link, which is safe and is stated in the guide). In Markdown source, table cells and entries that can't be edited the new commands are off; Add Link… there is as today. Because a caret at the end of a link counts, ⌘K there reads Edit Link…; to add a new link straight after a link, type a character first, as in Notes. The guide says so.

*Menu names.* The existing item **Link…** (Format ▸ Insert ▸ Link…, ⌘K) is renamed **Add Link…**, and reads **Edit Link…** when there is a link to edit. ⌘K does both, as Add Link… and Edit Link… share one key in Notes and Pages. A new item **Remove Link** follows it in the Insert menu. It has no shortcut; neither Notes nor Pages gives one. Remove Link is dimmed unless the caret or selection touches a link, and the group follows the editor-focus rule of 1.9.

*Edit Link… sheet.* The same sheet as Add Link, with the link's text and address filled in.

```
 Edit Link
 ┌──────────────────────────────────┐
 │ Text   Example site              │
 │ Link   https://example.com       │
 └──────────────────────────────────┘
 ┌──────────────────────────────────┐

 └──────────────────────────────────┘
```

- Title **Edit Link**. Buttons **Cancel** and **Done** (the Add sheet keeps **Add Link**). Return is Done when the address is valid; Escape cancels (Mac).
- **Text** shows the whole link's text, **Link** its address. An email link is shown without “mailto:”, because the field accepts a bare address (`LinkAddress`). An address this field can't accept (a link whose scheme the app doesn't open, kept as text) is shown as it is, Done stays dimmed with the existing “Enter a valid web or email address.” until it's corrected, and Remove Link still works.
- **When the Text row is shown.** The Text field can change characters, so it is shown only when the link's range is plain text on one line. When the range holds an inline image or other attachment, a line break, or more than one paragraph (possible after a Markdown import such as `[![alt](img)](url)`, or a link set over several lines), the Text row is not shown at all. Only the address and Remove Link are available, so no edit can drop an image or flatten paragraphs. An address-only edit changes the `.link` attribute over the range and never rewrites its characters.
- **Formatting.** When only the address changes, only the link's address changes; the text and its formatting stay. When the Text value differs from the link's text (compared as strings when Done is pressed, not whether the field was touched), the link's text is replaced with the new text, formatted as the first character of the link was, so a bold word and an italic word inside one link flatten to the first character's formatting. The guide says so. Its title (Markdown's link title, kept as the document has it) is kept.
- **The captured range.** The sheet acts on the range captured when it opened, not on the selection when it closes. Done changes that range, and focus returns to the editor at it (`.onDisappear { performFormatting(.focus) }` restores the captured selection, which is set to the link for an Edit Link… from the context menu).
- The sheet's height grows on the Mac to make room for the section (420 by 270 points). At large text it scrolls as the Add Link form does, and Remove Link is reachable by Tab as well as by pointer.
- On Cancel or when the document changed under the sheet (a sync, another window, locking) nothing is edited, as for Add Link today.

*Remove Link.* The link is taken off its whole text; the text, bold and other formatting stay. One undo step; Edit ▸ Undo reads “Undo Remove Link” (and “Undo Edit Link” for an edit). VoiceOver announces “Link removed.”

*Where else it appears.*

- **Mac, right-click on a link.** What the system's own menu already shows for a link in this text view (it can include Open Link and Copy Link) is checked first in the real app, and Edit Link… and Remove Link are placed with those items and don't repeat them. Edit Link… first selects the link under the pointer, then opens the sheet as ⌘K does, so the sheet's range and the selection agree; Remove Link acts on the link under the pointer at once and leaves the selection where it was. The menu comes from `NativeTextView.menu(for:)`, which already adds the picture menu.

There is no keyboard bar button for links today and none is added. With a hardware keyboard, ⌘K and the menu bar's Format ▸ Insert work as on the Mac. ### 2.5 Risks and open points

- **#2 and #3.** Import over an unopened library removes it once the restored library opens. That is the app's rule for every library switch and the sheet says so (“Restoring removes them from this device and ends any syncing with a server.”), but a library that couldn't be read could be of use to a repair; the guide says to copy the app's folder first on a Mac and to make a device backup on iPhone and iPad.
- **Import doesn't sign the device out** of its server; the device stays in the server's device list until it is removed in Devices on another device.
- **Erase now removes more**: every entry of the data folder it can move, and, in the default data folder outside tests, every Keychain item of the app's service (on the Mac only those with this folder's `keyAccount` prefix, so development and preview copies in the team's shared group aren't touched; on iOS all of them, because the hash changes after a reinstall). It is irreversible by design. What contains the risk: the list is built and saved before the commit, the former Mac server's files and an erase's own folders are never listed, and the protection list for earlier erases is separate from the sweeping list. A failed Keychain listing no longer stops Erase: the files go and the guide says Keychain items may remain, so a connection token can survive and is revoked in Devices on another device. Erase also can't move a settings file it has no permission to move; that stays the generic “Couldn’t Erase”, and the guide says deleting the app removes the files. On iPhone the device key stays in the Keychain after deleting the app, until the next install's Erase.
- **The Keychain listing is not verified on the system Keychain.** The unit tests use the memory store. Before shipping: the listing for `WhenUnlockedThisDeviceOnly` items on an iPhone and on a team-signed Mac, the Mac App Store build's access group (read `archive-mac.sh` and the signed binary's entitlements), the Mac hash prefix against a real library, and an item count before and after (2.1).
- **A settings file written by a newer version looks unreadable.** The screen says to update first; there is no button for it until the app is live. Erase appears only after a failed Try Again, behind authentication and an alert. The person with such a file and no update available has no route that keeps the journals, because the lenient reading and Start Over were removed.
- **App Lock and the screen.** The problem screen shows without authentication; it exposes only that the journals can't be opened (the lock screen and the app's icon already show that a journal exists), and Import and Erase authenticate. With settings that can't be read, App Lock is unknown, so the two actions authenticate regardless. A device whose passcode was removed while App Lock is on counts as approved (`checkDeviceOwner`), as for every Erase and as App Lock turning itself off does; no change.
- **TestFlight, the update text and the missing button.** One text names the App Store and TestFlight. Open App Store is not shipped until the app is live: add it then (see Layout).
- **The Erase alert can't say whether a server holds the journals.** It says so conditionally when the connection can't be read, and never claims the journals will be lost.
- **#15's iPhone and iPad edit menu** is a bonus, not a dependency; the Format panel and ⌘K are the route.
- **#13b** shows an unsaved choice. The notice row is the mitigation.

## 3. The owner decisions: implementation notes

### 3.1 #9 Export Archive asks for the device's authentication

- **When.** App Lock is on and the library isn't encrypted (`model.appLockOn && model.configuration?.encrypted == false`). Without App Lock, or for an encrypted library, nothing changes: an archive of an encrypted library is an encrypted copy that needs the recovery credential, and it can only be exported while unlocked. For libraries of recovery formats 3 and 4 the archive holds readable entries, images and earlier versions, and restoring needs no password, the same exposure as Markdown ([client-only-mac-lists-markdown-2026-10-05.md](client-only-mac-lists-markdown-2026-10-05.md) §3.2 gives that reason for Markdown).
- **Where.** At the start of `ArchiveExport.prepare` (`Model/DocumentTransferOperations.swift:141`), before the progress timer, as `MarkdownExportController.run` does (`Model/MarkdownExportOperations.swift:99-101`). Every way in uses `ArchiveExport.start`: Settings ▸ Backup, File ▸ Export Archive… and the Export Archive… button of the Erase alert, so all of them ask.
- **Mechanism.** `AppLockOperations.authenticateDeviceOwner(reason:)`. The reason is “Export an archive of your journals” (no full stop, like the other reasons, which the system adds to its own text). A device without a passcode goes on, as for Erase. Locking while the prompt shows ends the export (the function returns false when the app locked).
- **Cancelled and failed are different.** Today the function returns only true or false, so a cancel and a failure look the same. It returns the outcome (approved, cancelled, failed), and the callers that need it use it. A cancel stays silent: no message, no archive, the button is available again. A failure (Face ID locked out, authentication unavailable) shows “Couldn’t verify it’s you. Try again.” in the place the export's own failures show (`ArchiveExport.error`, the same message path as “Couldn’t export the archive. Try again.”), so the button doesn't look broken. The same two cases apply to Export as Markdown, which uses the same function, so both exports behave alike; Erase keeps treating both as “not erased”, silently, as the person is looking at the system's own failure message.
- **Copy.** The only new copy is the failure sentence. The existing footer for libraries without encryption (“An archive includes readable entries, images and earlier versions. Keep it private.”, `Views/ArchiveView.swift:19`) stays.
- **Docs.** [archives.md](archives.md) gets one line; the guide's backups page says the prompt appears with App Lock on and no encryption.
- **Test.** `ArchiveLifecycleTests` with `DeviceOwnerTestSupport`: App Lock on and no encryption asks, a cancel prepares nothing and shows nothing, and a failure prepares nothing and shows the sentence; App Lock on with encryption, and App Lock off, don't ask.
- **Not changed.** The Erase alert's Export Archive… button now authenticates, and Erase authenticates again after it: two prompts in a row on a rare path. A short window in which one prompt satisfies the next would be a new rule that weakens each prompt, so it isn't added; it is checked on a device that two prompts in a row are tolerable.

### 3.2 #10 Back from Merge Journals revokes the grant
