# Document-scoped image loading review

## Initial design and source review — 2026-09-21

**Approved for implementation with the concrete requirements below.** Reviewed `document-image-loading.md`, `AppModel.refresh`, selection/initial-selection/addImage/export paths, `EntryConflictReview` in SettingsView, ImageDescriptionsView, NativeEditor and RichText image rendering, and the current history/deletion-conflict loader lifetimes. No new rendered UI or independently rerun execution was inspected. The author reports a failing eager-loading fixture in `/tmp/journal-image-loading-before.log`; that reported result is not credited here as an independently inspected run.

The proposal addresses a real source-level problem: refresh traverses attachment references from all current records and only adds to imageData; it does not prune them when selection changes. Ordinary conflict preview uses that cache even for a remote-only document. Loading only documents being viewed is appropriate, preserves the quiet editor, and avoids making image availability a prerequisite for typing. The explicit limitation for a single large document is candid. No toolbar, setting, dialog or new permanent action is needed.

### Required implementation behavior

- **Patch only presentation for image arrivals.** Both current NativeEditor branches replace all attributed text when image count changes, reset typing attributes and collapse selection length to zero. Use the proposed image-only attachment-attribute update, retaining each block's journalImage metadata and full native selection range. Do not route this through user-edit mutation/undo registration, reset typing attributes, rewrite the document binding, or replace the whole text storage. Preserve undo/redo and marked composition. If composition makes an attachment presentation update unsafe, defer that update until composition ends rather than cancel composition. Updated attachment bounds can still move text even without string replacement: preserve a visible text/selection anchor when images above the viewport load, and verify the user is not jumped to the image or start of the document. Observe actual native behavior on each platform; setting the same numeric scroll offset alone does not prove a stable reading position when layout height changes.

- **Give loading and failure distinct, accessible image slots.** Use exactly “Loading Image…” while that reference has an active read and “Image unavailable” after absence, read failure or image decoding failure. The existing iOS placeholder is a fixed 220×40 raster, and the macOS failure branch can substitute the description without identifying unavailability. Do not reuse those shortcomings for the new state. Fit/wrap the placeholder text to semantic font size and available editor width, including largest text, with adaptive system colors. Keep the stored description intact; expose status plus description to accessibility, for example “Loading Image. [description]” or “Image unavailable. [description]”, omitting the description suffix when empty. Use the existing image ordinal where available. Do not announce every background transition. Description-thumbnail progress must have an accessible loading label and must not replace or disable the editable description. Keep it distinct from the existing description-sheet operation-wide “Loading Images…” status.

- **Own loads by actual displayed content, not only record ID.** Local/remote conflict versions share an ID. Include selected version/document attachment references and load generation in preview ownership; changing a conflict payload on the same side must invalidate stale loads too. Replace cache membership from the current draft's references, including unsaved inserted/deleted image blocks, and trigger this for direct draft assignments in recovery/import/navigation as well as ordinary select. Typing with unchanged references must neither restart reads nor flash placeholders. Retry failed/missing references on explicit refresh after download or reopening without continuous retry loops. Different loading/data states with the same dictionary count must repaint correctly.

- **Preserve lock and insertion boundaries.** Check captured store, selected record/version, generation and cancellation after every awaited read before publication; include store identity in the history loader audit, whose inspected final guard currently checks version/selection/lock but not store identity. Cancel/release preview-owned bytes on dismissal and replacement, and ensure removed native views do not retain visible image state after lock. Newly inserted bytes need an owned short handoff until the block enters the draft so immediate pruning does not discard them before rendering. The current addImage publishes bytes after an await without a selected-record/store recheck; address that race while changing this path. Never remove a document reference because bytes are unavailable. Export must continue obtaining its own required bytes rather than treating viewing-cache absence as content loss.

These requirements make the proposed behavior concrete; they do not introduce an additional interaction or visual design. Image-only patching and native placeholder sizing are approved implementation directions. If preserving composition/scroll/undo requires a different interaction, return for review before substituting one.

### Acceptance evidence

Use the proposed real-store model fixture to show no selected document means no retained viewing bytes; selection/reference changes prune and load exactly the current set; stale switch/lock/vault completions cannot publish; and refresh recovers absent images after bytes arrive. Add a remote-only ordinary-conflict image case and switch-version cancellation. Test late arrival with a nonempty text selection, typing style, undo/redo and active composition where available; require exact unchanged document/reference metadata across loading, missing and decode-failed states. No arbitrary memory threshold or composition-only mock test is needed.

Inspect actual normal/largest loading and unavailable placeholders, loaded-image arrival during editing, description thumbnail progress and remote-only preview rendering. Retain focus and readable body content while images appear. Source review cannot establish VoiceOver narration or interactive Mac behavior on the locked desktop. Existing history/deletion previews may retain their current presentation during their own preparation, provided ownership and reference preservation remain intact. Performance beyond the reduced retained source-image set remains a separate measurement.

No production source was changed by this review.

### Findings sent to the implementation author

- **P2 — Normalize macOS attachments restored by undo.** The inspected macOS `textDidChange` calls `refreshImages`, but that method returns when image keys, loading IDs and appearance have not changed. An attributed undo restoration containing a former loading placeholder can therefore remain stale after the bytes have already arrived. iOS's custom `restore` now forces a presentation refresh to solve precisely this snapshot problem. Apply equivalent handling to macOS native undo/redo and verify its actual undo behavior; the iOS test does not establish AppKit behavior.
- **P2 — Preserve image loading state and width during paragraph formatting.** Both paragraph-formatting paths call `RichText.render` with default loading state and width. A selection containing a still-loading image is reconstructed as “Image unavailable”; the subsequent conditional image refresh need not run because its observed cache state is unchanged. A loaded image may also regain the default 620-point width. Pass the current loading IDs and editor width into those render calls, and audit the macOS image-insertion render call for the same width/state omission.

## Initial-layout width correction proposal — 2026-09-21

**Approved for implementation within the existing presentation-only design.** The author proposes native width-change callbacks (`layoutSubviews` on iOS and `layout` on macOS) that ask the coordinator to refresh only attachment presentation when actual width changes, including the first nonzero layout. Width becomes another presentation-state input alongside image IDs, loading IDs and appearance, with updates deferred under marked composition. No controls, copy or navigation change.

Independently inspected `artifacts/image-viewport-first/D155C9CC-1148-47EA-9DFC-DB7612470751.png`: “Loading Image…” is broken into several very narrow fragments while body paragraphs use the available editor width. Current source initially renders using `max(40, view.bounds.width - 20)` but has no width-change refresh trigger; the zero-width makeUIView diagnosis is consistent with that visible defect. This is a material initial-layout presentation defect requiring correction.

Implementation requirements: enter a reentrancy guard before any ensureLayout/anchor work, because attachment layout can trigger the native layout callback again. Compare usable width with a small pixel tolerance and ignore zero/nonfinite transient geometry; do not refresh for height or scroll-offset changes. Keep rendering width consistent with the text container/insets. Record successfully rendered width only after the patch, so a callback during marked composition leaves a mismatch for composition-end processing. Use weak coordinator callbacks and preserve the existing selection, typing attributes, undo registration, document metadata and visible-anchor protections without publishing a document mutation or replacing the whole string. Inspect first-layout normal/largest placeholders after correction, and assert meaningful attachment width in the hosted fixture so a text-preservation-only test cannot accept this visual defect.

The author reports that a separate initial scroll test failure came from harness window takeover, corrected with an attached window scene, window level and settled initial layout. Independently inspected `/tmp/journal-viewport-tests2.log`, which reports both hosted tests passing and `TEST SUCCEEDED`; the revised harness source/captures have not yet been independently reviewed here. No production scroll defect is inferred from the superseded harness failure, and no actual viewport acceptance is granted solely from that log.
