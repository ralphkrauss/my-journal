# Entry archiving — independent design review

Reviewed 2026-09-20 against `entry-archiving.md`, the user's requested context-menu Archive action, project guidance, and existing lifecycle/archive/agent contracts. This is preimplementation review; no archiving source or UI is approved by implication.

## Verdict

**Direction approved; revise three integration details before frontend implementation.** Archive Entry / Unarchive Entry are clear, reversible native actions and need no confirmation. A single Archived collection, no writing-surface badge, month grouping and the unchanged editor are a restrained extension of the current app. Keeping journal membership, content, history and sync behavior intact matches the expected meaning of archiving. The proposal correctly distinguishes this action from encrypted archive files and deletion.

## Required clarifications

1. **Make cross-journal Archived navigation unambiguous.** Because Archived aggregates all journals, show the current journal name as secondary row context in this collection only, with Untitled Journal fallback and the same identity available to VoiceOver. Otherwise a user cannot predict where Unarchive returns a similarly titled entry. “Original journal” should mean the entry's current journal membership, including an explicit move made while archived; it must not mean an older historical journal. Define New Entry/creation-options behavior while Archived is selected rather than accidentally using the last hidden journal selection. A simple acceptable policy is to disable creation in Archived until a journal is chosen, while keeping existing empty-state copy and high-level navigation available. If another policy is chosen, make its destination explicit before creating content. Define selection after archiving a nonselected row too: only an entry that actually leaves the current collection should clear the editor; no unrelated draft or collection should be reset.

2. **Extend the archive-file import preview's disjoint destination counts.** Existing reviewed preview copy is “N entries in journals”, “N in Recently Deleted”, and conditional “N in Unavailable”. Once archived entries live in Archived, including them in the first count misdescribes where imported entries appear. Add conditional **“N in Archived”** when nonzero, between live entries and Recently Deleted, and use the same atomic lifecycle snapshot/precedence as every other reader. Keep the prior first two required zero categories (live and Recently Deleted); Archived/Unavailable can remain conditional. Historical/conflict copies must still not inflate current-entry counts. This is a consequence of introducing the new visible location, not a new archive-export feature.

3. **Specify individual recovery when the parent is deleted.** The current proposal defines directly deleted archived entries and whole-journal restoration, but the existing individual entry flow can also restore a deleted parent along with its selected entry. State explicitly that an individually recovered archived entry becomes unarchived, while other inherited children retain their archive state when that parent is revived. Keep the parent's existing explicit restoration consent and explain the selected entry's unarchive result; Restore and Move similarly clears only the selected entry's archive state. A whole-journal Restore must preserve every child's archive state. This distinction must be reflected in actionable copy, final captured scope and tests, so a user is not surprised by archived siblings reappearing in ordinary lists.

## Accepted lifecycle and privacy behavior

Deleted/unavailable parent precedence is appropriate, including archived children of unsupported/conflicted parents. Archive must not hide such entries from their recovery route or make them editable. Archived entries stay editable/exportable with history, and Move preserves archive state. An explicitly chosen permanent-deletion-conflict recovery or historical copy can clear archive state to make the resulting entry visible, while source versions retain their actual state. Permanent deletion still counts all current children, including archived children, and its minimal marker must carry no archive status. Templates must reject the field rather than silently treating it as applicable.

Including archived entries within an already granted journal does not broaden the journal scope: archiving is organization, not access revocation. Retain the existing conflict/unsupported/deleted/lock exclusions and read-only enforcement, expose archive status in returned data, and document this behavior in the agent contract. Prefer the short disclosure **“Archived entries are included.”** in the grant explanation or accessible-scope description so users do not mistake removal from the timeline for hiding content from an authorized agent. Do not introduce another consent prompt for each archive action. Archive export/import must preserve state and permissions must remain excluded from archives as before.

## Copy, errors and accessibility

The proposed action labels, Archived collection name, No Archived Entries/Entries you archive appear here empty state and Search Archived Entries are suitable. Exact minimal stale-state copy can be **“This entry’s archive status changed. Review it before trying again.”** A vanished/deleted/unsupported/conflicted target should use its actual existing reason and route, not an inaccurate archive-status error. Reopen/refresh must not secretly repeat the action. Keep the proposed committed-refresh failure copy distinct from a failed mutation and reconcile the retained draft before lock/quit flush.

Use native sidebar/menu icons only where already conventional, full wrapping labels and contextual keyboard/VoiceOver actions. All mutations should target captured identity after settling the draft, update only archive state against the latest supported record, and reject stale expected state. Selected-draft export must remain available after a failed save; archive/unarchive must not become a route around that failure. No routine completion toast or needless confirmation is needed.
