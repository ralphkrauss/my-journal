# Export operation lifetime review

## Independent proposal/source review — 2026-09-21

Reviewed `export-operation-lifetime.md`, the current `AppModel.entryExport`, `prepareArchive`, `inspectArchive`, `discardImportedCopy`, session-related property observers, and `EntryExportView`/archive view success and error handling. No production edits or reviewer test reruns were performed. The reported pre-cancelled regression is still pending evidence and is not counted as a demonstrated test result here.

The proposed irreversible vault-session generation, original-store capture and snapshot semantics are sound. Retaining a captured unsaved draft while ordinary editing continues is an appropriate export contract. Cancellation should remain quiet; no layout, copy or interaction redesign is needed. However, two publication boundaries must be explicit before implementation approval:

1. **Carry ownership through archive-preview preparation.** `ArchiveImportView.inspect` awaits `result.store.lifecycleSnapshot()` after `model.inspectArchive` has returned. A model-only generation check before that return leaves a second lock→unlock or store A→B→A window before `preview`/`prepared` publication. Either produce the summary within the model's checked operation or carry the captured session through the view and validate it after that final await. The same rule applies on its error branch. Checking only `model.locked`/task cancellation at that point is insufficient to cover store changes or a missed/coalesced lock observation.
2. **Normalize stale failures as well as stale successes.** An original-store attachment/archive read can throw after session invalidation. If validation only follows successful awaits, the old error reaches a newly unlocked view and becomes an irrelevant failure message. Catch failures at the operation boundary, revalidate the captured session/cancellation, and surface a cancellation outcome for stale work before considering the underlying error. Preserve genuine errors from the current session. Apply this to pending-save failure too: revalidate before presenting “Save your changes…” from an obsolete operation.

Cleanup must cover both successful stale completion and thrown work that may have created a partial generated destination. Use the operation's unique destination and ownership-transfer flag; never infer cleanup ownership from a mutable current document or the user-selected source URL. Confirm the archive implementation's own partial-failure cleanup before duplicating it. Existing `discardImportedCopy` protects the configured active folder and requires an import staging location; retain those protections. Cancellation after returning a generated URL still requires caller cleanup, which the current export view already attempts.

The entry exporter should check cancellation/session before starting and again after all relevant awaits and final serialization, using a once-captured image cache and store. Begin neither entry export nor archive inspection during `replacingVault`. A generation separate from the image insertion generation is appropriate because ordinary draft editing should not cancel an intentional snapshot export.

Suggested focused verification: pre-cancelled plaintext refusal; ordinary unsaved snapshot export; independently invalidated lock→unlock and store A→B→A captures; current-session genuine failure versus stale failure suppression; archive staging cleanup without touching the selected source. Tests should exercise meaningful publication decisions rather than merely assert UUID changes. Existing native success screenshots remain applicable to unchanged presentation, but do not establish these timing properties.

**Outcome: direction accepted; address the two explicit publication/error boundaries above in the proposal before implementation.** No new visual or copy findings. Subsequent review can be confined to these source-lifetime details and relevant execution evidence.
