# Version-history recovery proposal review

Date: 2026-09-20. Independent preimplementation review of `history-recovery.md` and current VersionHistoryView/JournalHistoryView. No new recovery implementation or tests reviewed.

## Outcome

The proposed entry/template copy semantics and metadata-only journal restoration are sound. Explicit destination selection avoids recovering into a deleted or unrelated journal; creating a new identity preserves the source and conflicts. Separate Restore as New Template prevents the current view's entry-oriented action from confusing template recovery. Restore Settings accurately limits the change to name/default template and retains journal lifecycle state. **Request two bounded failure/confirmation clarifications before implementation.** The normal layout and action labels do not need redesign.

1. **Specify recovery for current unsaved edits and make export reachable in the active sheet.** Restoring a historical copy navigates away from the current draft, so explicitly await the existing final-save gate and retain the draft if that fails. The history sheet must not close, replace the editor snapshot, or claim the historical restore failed after its copy already committed. For a precommit current-entry save failure, retain version/destination and provide active-sheet Export Entry for the unsaved current draft, clearly distinguished from exporting the selected historical version or the archive. Specify a retry that actually retries/settles the failed save, or copy/export plus close/save guidance; avoid the ineffective retry recently corrected in image descriptions. Unsupported history should expose lossless Export Archive from the history sheet itself, rather than requiring a hidden root action. Explain which content each export includes; ordinary saved historical preview is not an export of newer unsaved text.

2. **Define the settings confirmation's refreshed and already-applied outcomes.** Capture selected historical identity plus current name/default-template identity before opening the one confirmation. Revalidate historical membership and the current supported/conflict-free parent within the same write as the metadata patch/history preservation. If current metadata changes, clear the confirmation and require fresh current-versus-historical review followed by an explicit Restore Settings; never auto-submit after refresh or conflict review. If the name/default reference already match the selected historical values, show “These settings are already in use.” with Done and no redundant mutation/history record. Define active-sheet Review Changes for a conflicted current parent, and keep missing/unsupported parent failures read-only/exportable. A selected historical metadata record that disappears must use the stated unavailable-version/reload handling just like entry history.

Record those rules in the proposal and re-review before implementation. They do not expand lifecycle restoration or require another confirmation for creating an entry/template copy.

## Native layout and copy conditions

- Entry/template history is already an explicit preview/action surface: Restore as New Entry/Template needs no extra confirmation. Settings restoration has exactly the proposed current-versus-historical confirmation, with clear “Current” and “Restore” labels and one Cancel/Restore Settings pair.
- Use None for no default template, an available template's current readable title when known, and Unavailable Template for a preserved missing reference. Compare actual IDs in the write, not the displayed names. Distinct templates may have identical names; showing the same visible title must not hide an identity change in the confirmation. Add brief context if necessary to distinguish that case without exposing raw IDs as ordinary copy.
- Keep New Journal creation separate from the restore action. Its commit/refresh failure must not suggest creation failed or encourage a duplicate journal; keep the new destination unselected as proposed. Reuse its preservation/owned-task behavior, but ensure unavailable/conflicted historical sources remain recoverable and the nested flow does not inherit a current-entry editing eligibility requirement.
- Disable selected-version/destination changes as well as repeat restore while committing. A captured source ID must survive root navigation changes; stable historical selection should not be represented only by a mutable picker index. Use the immutable authenticated version identity or equivalent complete membership evidence, including for equal timestamps.
- Missing bytes need a meaningful read-only preview indication and preserved references; do not imply that a restored copy has recovered image bytes that are absent. Unsupported content should never be round-tripped through the rich-text editor before copying/exporting.
- Preserve the explicit distinction between entry date and historical save timestamp. Restore as New Entry keeps its historical entry date as proposed; version picker uses save time with clear ordinal disambiguation. Accessible picker options should include both time and ordinal when needed.
- Error announcements, scrollable action access, and lock clearing must include nested creation, conflict review, export, and settings confirmation. The busy indicator must name the actual operation. Do not use color as the sole indication of failed recovery.

## Verification

The proposed real-store tests target appropriate risks. In addition, exercise an existing current-draft save failure before navigating to a restored copy, stale settings after opening confirmation, an already-matching settings result with no duplicate history mutation, and missing/unsupported historical membership. Preserve pending immutable retry bytes and old versions while adding the recovered record/settings revision.

Native/model evidence should hold the actual DB commit before model reconciliation and lock, verify committed refresh failure prevents a second copy, and distinguish transient history-read error from No Earlier Versions. Actual preview/restore/reopen plus largest-text sheet actions should be inspected; screenshots or picker labels do not establish VoiceOver reading of inline historical images. Offscreen Mac evidence retains its prior limits.
