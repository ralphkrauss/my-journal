# Image descriptions: native iOS form layout

The reviewed scrolling sheet saves safely but actual largest-text keyboard captures still cover the current edited line. Bounded fields and focus scrolling improved but did not resolve it; an extra keyboard event did not help and was removed. Retain all image-description data/save/reload/lock behavior. This proposal replaces the custom iOS ScrollView/VStack arrangement with a native Form so keyboard adjustment and focused-row positioning are managed by the native form container.

On iOS keep the Image Descriptions navigation title and Cancel/Done toolbar. First section contains the existing short explanatory text. Each image has a native section with Image (or Image 1, Image 2) header, preview or Image Unavailable in one row, and the same native vertical Description field in its own row. It retains its per-image accessible name, system spelling/correction, system text size, one-through-three visible line range and full local string. Let the form use its standard background, row separators and insets. Images remain aspect-fit with the existing maximum dimensions; do not shrink text or add custom colors. A final action section contains Copy Descriptions and conditional error/reload/retry/progress content. Copy remains an explicit action, not automatic clipboard access.

Use native grouped form styling and native row layout rather than custom rounded text-field borders on iOS. Keep the Mac layout unchanged. Extract shared image field and recovery actions if needed to avoid duplicating state or mutation logic; do not create a new model. Remove manual focus/ScrollViewReader positioning on iOS because the native container should own its row positioning. Keep focus identity only where needed for privacy clearing; no autofocus, timers, selection changes or forced scrolling on text edits.

Empty/locked/error/loading/committed states stay as in the approved original design. Explicit lock clears local strings and focus and dismisses. Unsupported/missing image bytes stay editable through their reference; normal and error actions retain their existing enablement and recovery behavior. Larger accessibility text must remain readable and all actions reachable. Current image ordinal remains accessible if its preview scrolls out of view.

Before considering this fixed, use the actual simulator with largest Dynamic Type and dark mode: focus the field, enter longer-than-three-line text, continue typing, and inspect the visible caret and full edited line above the keyboard. Inspect earlier text editing, full-value save/relaunch preservation, and Copy. Also inspect normal-size layout and verify Mac still builds. If the native form still occludes the line, investigate actual safe-area/inset evidence; do not pile on keyboard notifications or reduce text size.


## Disposition

Reviewed as an available alternative, not implemented. Authoritative UI hierarchy showed the previous test drag still started in the separate prediction surface: Keyboard top was 583 points while inputView/predictions began at 539. Corrected drag starts above inputView and outside the nested field. Actual continued-edit screenshot artifacts/image-outer-scroll-previews/7475429B-FA2D-4081-A405-914B4CB0BE62.png shows the whole active range and caret clearly above the keyboard. The existing reviewed layout can scroll normally; the earlier captures did not prove otherwise. Retain the current layout instead of replacing it on a faulty gesture assumption. See image-description-keyboard-review.md for independent inspection and evidence limits.
