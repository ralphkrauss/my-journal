# Imported image type review

## Independent proposal review — 2026-09-21

**Approved for implementation with the validation and ownership boundaries below.** Inspected `imported-image-type.md`, `AppModel.addImage`, the macOS file-drop implementation and RootView's picker/callback wiring. The current non-PNG-as-JPEG drop fallback and filename-derived picker metadata can mislabel unchanged bytes. Central byte-derived detection addresses that concrete portability defect without expanding image editing or replacing the native import interaction. No source was changed or execution evidence inspected by this review.

Preserving the original Data is the right contract: do not re-encode for MIME detection, flatten animation, strip metadata or repair old documents opportunistically. A recognized ImageIO source, positive frame count and an image-conforming UTType with a usable image MIME type provide a reasonable narrow metadata gate. Do not describe source recognition alone as proof every frame fully decodes or every browser can render the format. If detection or MIME mapping is unavailable, reject before attachment storage rather than silently defaulting to JPEG. Existing attachments, archive imports and sync remain outside this correction.

The existing error presentation with “This file couldn’t be read as an image.” is concise and appropriate for picker/drop files. It introduces no technical format terminology, new dialog or persistent clutter. Clipboard failures may originate from image data rather than a literal file; that wording is still understandable in the shared importer and does not justify a new error-flow design. The no-layout/no-control/no-focus-change scope is approved without a mockup. Actual error presentation still requires a bounded check; source review alone does not establish it.

Removing the authoritative mediaType parameter from `AppModel.addImage` prevents callers from bypassing byte-derived metadata. Keeping the existing editor callback shape temporarily, with its hint explicitly ignored at RootView, is acceptable narrow scope. Preserve lock/store/entry ownership checks around storage and image priming. Do not publish late failures into a different entry/vault or use this correction to relax insertion ownership. Detection before any suspension should not create an attachment on invalid input.

Meaningful verification should use real encoded PNG and at least JPEG/TIFF bytes, check the resulting DocumentBlock mediaType and exact stored bytes, and reject unrecognized input without adding an attachment. A misleading filename/caller hint should not alter the result. Keep the fixtures small; framework format-table coverage and broad decoder testing are unnecessary. The native insertion/loading regressions should continue to pass. Multi-frame preservation follows from exact-byte storage but animation playback is not promised. Live Mac drag/drop, VoiceOver, all image formats and browser export compatibility require separate evidence and are not accepted by this proposal review. Implementation and focused verification remain pending.

### Internal signature refinement

Removing the unused type hint from the native image callback and its call sites is also approved, and preferable if the change remains mechanical: transport bytes to the single classification boundary rather than preserving misleading metadata in an internal API. This does not change the reviewed user interaction or require a new design pass. Checking ImageIO source status is complete in addition to source recognition/frame count is a reasonable rejection of obviously incomplete encoded input; it still does not prove full pixel decoding of every frame. Keep exact-byte preservation and the same concise error behavior.

## Implementation and focused Mac evidence — 2026-09-21

**Accepted for source correctness and the inspected import-state evidence; no remaining finding for the metadata correction.** Inspected `Model/ImportedImage.swift`, `AppModel.addImage`, bytes-only native callbacks/RootView wiring, `ImageImportTests.swift`, and the import-test result in `/tmp/journal-image-type-apple.log`. The real Mac import test passes in 0.006 seconds; the log contains `TEST SUCCEEDED`. No reviewer tests were rerun. The final rerun including the subsequently completed catch ownership guard and targeted iOS verification were pending, so this does not claim their execution results.

The helper requires an ImageIO source, positive frame count, complete source status, an image-conforming UTType and preferred MIME mapping. It has no extension/JPEG fallback or re-encoding. AppModel validates before storing, stores the same Data, and retains the post-await store/entry/lock/replacement/cancellation checks before priming/returning. The catch now uses those ownership checks before publishing an error. Native paste/drop and picker callbacks pass only bytes; the stale hints are removed without adding visible interaction.

The test encodes actual PNG, JPEG and TIFF images, runs each through AppModel and the isolated encrypted store, verifies the returned MIME and exact recovered bytes, and checks the HTML data URI declares the corresponding MIME. Invalid bytes yield the reviewed error, no returned block, unchanged pending-attachment IDs and unchanged draft. This meaningfully protects the prior non-PNG mislabeling and rejection-before-storage behavior. It does not claim a misleading filename was interactively chosen; filename/type hints are absent from the authoritative API.

Complete-source recognition is still not exhaustive pixel/frame decoding, and TIFF HTML declaration is not proof that a browser displays TIFF. Exact-byte preservation establishes no conversion in this path, not animation playback or old-attachment repair. The error string is state-tested but no live error-dialog screenshot was inspected. Live drag/drop, VoiceOver and full format/platform coverage remain outside this bounded acceptance.
