# Journal lifecycle proposal: inherited visibility

Unimplemented proposal. Revised user-facing semantics are independently approved in journal-lifecycle-review.md; shared implementation and correctness evidence remain required before exposure.

The current proposed cascade writes individual child tombstones and uses a deletedWithJournal boolean. That needs a distributed transaction/generation protocol to restore reliably across partial deliveries. A simpler hierarchy model may satisfy the product without adding that protocol:

- Delete Journal changes only the parent journal's deletedAt. An entry remains in its existing journal, with its own body and independent deletedAt untouched. Its effective location is Recently Deleted if its parent is deleted OR its own deletedAt is set. Missing parents are unavailable, never assumed live.
- Restore Journal clears only the parent tombstone. Entries that were live before hiding become visible again; independently deleted entries remain in Recently Deleted. There are no child deletion messages to arrive after restoration. Repeated parent delete/restore cycles are ordered by the existing per-record revision/conflict protocol, never wall clocks.
- An entry moved to another live journal no longer inherits its former parent's deletion. Concurrent parent deletion and child movement have independent identities and do not mutate one another. An offline newly created entry arriving under a deleted journal is retained and appears with that journal in Recently Deleted; it is not silently lost.
- Selecting a child of a deleted journal offers Restore Journal (which explicitly restores all non-independently-deleted children), or Move Entry… to recover just that entry into an existing live journal. If the selected entry was independently deleted, moving it also explicitly clears that entry's tombstone, with a Restore and Move action. This changes the earlier parent-plus-only-one-child restoration proposal and therefore requires independent design review before implementation.
- Restore Journal confirmation says “Restore ‘[name]’?” with “Entries deleted with this journal will return. Entries you deleted separately will stay in Recently Deleted.” The live-child count is informational and local; the semantics apply to the whole journal, including entries subsequently arriving from offline devices.
- Delete Journal confirmation says “Delete ‘[name]’?” with “[count] entries on this device will move to Recently Deleted. Entries from other devices will appear there when they sync.” The confirmed locally known set is rechecked atomically; changed membership/name prompts renewed confirmation. No client promises a globally complete count while offline.
- Agent access uses effective visibility too: a deleted parent cannot remain readable through a grant just because child tombstones have not arrived. Existing explicit granted journal IDs persist but return no deleted contents unless a separate future grant explicitly supports trash. Search and editor navigation must use the same rule.

This is a proposed simplification of representation, not permission to omit single-entry recovery. Move out of a deleted journal supplies that route while preserving parent deletion. Existing legacy deletedWithJournal tombstones (including restored archives) require a defined compatibility migration or explicit refusal; do not silently reinterpret independently deleted entries. Entry conflicts remain explicit; a journal metadata conflict is reviewed before changing parent lifecycle.

Required real-store/replica tests: both parent-before-child and child-before-parent delivery; restore before an offline child's arrival; repeated deletion/restoration cycles; independent child deletion; concurrent move out; stale confirmation set; agent/search/editor effective visibility; legacy tombstones and unsupported parents. Do not expose the feature until shared semantics are used by every reader.

## Review refinements

When no live destination exists, the captured Move Entry recovery picker offers New Journal… as a nested native name sheet (Name, Cancel, Create). Successful creation returns to the same captured entry and destination picker, showing the new journal unselected; the user explicitly chooses and moves it. Do not switch the root draft as a side effect of creating this recovery destination. Other destinations remain usable if any exist. Parent and siblings remain deleted.

Parent-hidden entries whose own tombstone is nil use Move Entry… / Move and “Only this entry will move to the selected journal.” Independently deleted entries use Restore and Move… / Restore and Move. Restore Journal uses a separate confirmation explicitly including later-synced entries and excluding separately deleted ones. These labels supersede the earlier Restore Journal and Entry proposal.

Unavailable-parent entries appear in a separate “Unavailable Journals” collection reachable from the journal menu, with read-only title/date/document preview and lossless Export Entry. They are never mixed into the ordinary editable timeline or exposed to agents. For missing parents, use the previously reviewed configured-sync/local-only guidance and real actions. Unsupported parents use update guidance. As sync supplies a supported parent the entry returns to its proper collection without duplicating its identity. This recovery collection also exposes ambiguous legacy entries.

Legacy boundary: old deletedWithJournal=true records are preserved but treated as legacy rather than assigned guessed inheritance. Do not bulk-restore them as part of new parent restoration. They remain individually visible in Recently Deleted when their parent is available, or Unavailable Journals otherwise. Offer an explicit Restore and Move to a supported live journal; that atomic user action clears that entry's legacy marker and own tombstone while preserving its content/history. Explain “This entry was deleted by an earlier version of Journal. Choose a journal to restore this entry.” If its document/record contains unsupported fields, disable mutation, show update guidance and lossless export instead. New writes never set deletedWithJournal=true. Restoring a parent explains any legacy entries remain in Recently Deleted for individual recovery; count them locally, without claiming remote completeness. No automatic guessing about original deletion cycles occurs.
