# Independent proposal review — 22 September 2026

Reviewed `notes-alignment-revision.md` against the independent audit, supplied Notes photos, and current source. No implementation or builds performed. The requested hierarchy, bottom phone actions, input accessory, Done semantics, adaptive iPad split, targeted Mac toolbar ownership, simplified setup, separate Agent Access, and removal of forced source mode are the right direction. The reference photos are used as layout evidence, not as private-content fixtures. The new user requirements supersede the earlier source-only and command-picker approvals.

**Verdict: resolve the following material specification gaps before implementation.** This does not request additional product scope; these are necessary consequences of the proposed routes and structured editor.

## 1. Expose compose destination in global collections

“Last live journal or Default” still silently targets a journal on Journals/All Entries/global search. A person can reasonably expect composing in All Entries to ask where the entry belongs, particularly after inspecting a different journal. Specify a visible destination before creation. A minimal native journal menu from Compose is sufficient when more than one live journal exists; one journal can create directly. If remembering a choice, display it in that menu and do not create until the person selects it. No journal should open New Journal, then create the entry only after successful journal creation. The same rule must apply to templates from global collections. Capture the destination identity and template identity at activation and revalidate both before mutation; do not retarget when selection or collections change while the picker is open.

## 2. Finish immediate-template dismissal, empty/error, and keyboard semantics

Immediate selection is reasonable for a lightweight picker, but “Cancel by tapping outside/Escape” is not a complete compact-sheet or assistive-technology dismissal path. Give compact presentations a native Close/Cancel affordance (an accessible icon is compatible with no visible heading or Create step); popovers can retain outside dismissal and Escape. Search should receive focus once on explicit open. Up/Down moves the active choice; Return activates the highlighted live choice, not an arbitrary typed name; merely filtering/highlighting never creates. Keep row targets at least 44 points on touch and ensure long names/large text scroll instead of disappearing.

Specify concise empty/no-match states and a failure state with the picker still open and selection retained. For example **No Templates** with an available route to template management, **No Results**, and **Couldn’t create the entry. Try again.** with retry where the failure is retryable. Hide duplicate activation while creation is pending. Explain deleted template/destination recovery and accessible duplicate-name disambiguation. These states need not add prose to the normal picker. The proposal must not delete the only way to cancel a mobile sheet in order to satisfy “minimal.”

## 3. Resolve structured editing semantics rather than delegating them to fields

The coverage matrix is substantially better, but “Return remains text input or advances according to native field semantics” leaves a core writing operation undefined. Choose a single table-cell behavior across native clients. A practical contract is Tab/Shift-Tab traverse cells, Return ends/advances cell editing without silently adding a row, and explicit Add Row adds rows; if multiline cell content is intended, define how it serializes within GFM's single-line-cell grammar and which command inserts a line break. Define last-cell traversal, empty table creation, header-only tables, and focus after row/column deletion. Protect meaningful contents when deleting a row/column through coherent undo and a clear explicit action.

For lists, specify Tab/Shift-Tab or native indent commands, Return continuation, empty-item Return exit/outdent, task-state toggling, and numbering through nested/loose content. For code, Return inserts a literal newline, Tab/indent does not jump to the next block, and a clear keyboard route exits the block. Table/list/code toolbar actions must remain usable with software and hardware keyboards.

The proposed mix of multiple native text leaves and an ordinary flat editor also needs a clear selection/undo contract: how users select/copy across blocks, where paste of multi-block Markdown is inserted, and how a single entry-wide undo sequence survives focus moving between table cells, paragraphs, code, and modes. Independent field undo stacks are insufficient. Define command targeting when title/search is focused and ensure Done commits any current IME composition before resigning. One precise paragraph per construct plus an entry-wide selection/undo rule is enough; do not start building an unspecified second editing system.

## 4. Make failure-safe native Back concrete

The intent to wait for saves is sound, but default navigation-stack pop and swipe-back can remove the editor before an asynchronous flush completes. Specify an implementable route transition policy: intercept a requested transition while ending composition and saving, complete it only on success, and retain the existing visible editor with recovery controls on failure. Preserve native interactive Back behavior where possible; do not leave an invisible draft behind a popped destination. The same boundary must cover Done followed immediately by Back, journal/collection changes, deletion/restoration, and a size-class transition during save. A route keyed to stable identities and a single transition coordinator is an acceptable implementation strategy, but the observable result and pending/failure behavior must be defined. Avoid a new confirmation for successful ordinary navigation.

## Nonblocking clarifications to include

- The new setup layout is approved in principle. Retain an exact recovery warning and failure/retry copy, clear transient passwords on Cancel, preserve them on Back, and keep the sheet's action buttons reachable with large text/keyboard. The first-page paragraph should say encryption protects stored writing; existing security behavior remains binding.
- A bottom/accessory mode action labeled View Preview must lead to the intended editable formatted view, not a read-only substitute. Specify the icon and selected/current-mode accessibility state without exposing raw implementation terms in normal writing.
- Define where the nonediting bottom toolbar lives with a hardware keyboard and floating iPad keyboard. Do not make important commands depend solely on an input accessory that the OS may omit. Scrolling an accessory at large text must leave every command discoverable by VoiceOver and keyboard.
- Native search placement should adapt to deployed OS APIs; do not promise current-OS bottom glass on earlier OS versions. A functional native bottom toolbar/search presentation is sufficient.
- macOS's source placeholder fix and context-menu cleanup are well scoped. The fixed title height warrants inspection and correction only if actual long-title/text-size behavior clips; offscreen toolbar omissions remain evidence limits, not proven live defects.

## Gate outcome

Re-review the amendments above before frontend implementation. The overall direction is approved, but the implementation gate is not yet closed. Later actual-UI review must substantiate navigation, picker dismissal, input accessory/Done, and structured rich editing—not just static visuals or successful parsing. Preserve the specified no-loss, conflict, offline, accessibility, and native text-service boundaries throughout.

## Shared native-text table refinement review — 22 September 2026

Reviewed the proposed replacement of inline table attachments/cell controls with tagged, tab-separated cells inside the entry's native attributed text view. No implementation or builds performed.

**Do not approve plain tab stops plus grid drawing as the complete table implementation.** A shared text view is attractive for native selection, IME, rich styling, and a single undo manager. It can be approved as an internal storage/editing strategy only with genuine cell-aware layout and accessibility; a visually decorated tab-separated paragraph is not sufficient. The earlier attachment/cell-control design remains the approved fallback while the following questions are unresolved.

1. **Layout must behave as cells.** Native tab stops align short single-line values but do not constrain a long cell's wrapping to its column. A value can overrun the next stop or wrap across the full paragraph, disconnecting the grid and subsequent cells. Define a cell-aware layout strategy on each platform, including long unbroken values, inline marks/links, empty cells, varying row heights, alignment, narrow-width horizontal scrolling, and large text. Mac NSTextTable may supply real block layout; it does not establish equivalent UIKit behavior. A bespoke text layout implementation is possible, but must not be presented as a routine tab-stop change.

2. **Structure must be editing-safe, not merely tagged.** Intercepting Tab/Return does not cover Backspace/Delete at boundaries, Cut, selection replacement across cells or across body/table, drag/drop, dictation, rich paste, autocorrection, or IME marked-text updates. Define the behavior of each structural boundary. Ordinary text deletion must not silently merge columns or rows or leave invalid metadata. Structural deletions must be explicit, predictable, and undoable; copying and replacing a cross-cell selection must not flatten the surviving table accidentally. Stable metadata must survive attributed-string replacements and native undo/redo without relying solely on inherited typing attributes.

3. **Prefer actual empty ranges over editable sentinel characters.** A zero-width placeholder can attract the caret, enter marked text, inherit formatting, appear in search/selection, or escape through pasteboard/plain-text export. If sentinels are indispensable, define how the caret and selected ranges map to semantic content and prove they never appear in source, clipboard flavors, accessibility values, find results, or history. Excluding them only during final storage is insufficient. Deleting a placeholder must not delete the cell identity. Table traversal must distinguish literal content from structural separators rather than normalizing arbitrary tabs everywhere.

4. **Accessible cells need a real navigation model.** Row/column labels attached to an entire text view do not make cells independently inspectable or editable. Specify VoiceOver focus per cell, row/column/header announcements, selection and insertion-point feedback, supported activation/editing actions, and returning from a cell to surrounding text. On iOS, establish how accessibility elements representing cells coexist with UITextView's native text-input accessibility; do not hide the native editor and substitute static labels. Keyboard and Full Keyboard Access routes must reach explicit structural controls. Avoid duplicated or contradictory announcements from virtual cells and the underlying text view.

5. **Specify clipboard and source mapping.** Whole-table copy should provide Markdown/plain-text and a suitable rich representation; partial cell text should copy ordinary selected text; a selection crossing cells/body must serialize a coherent meaningful fragment. Preserve literal pipes, escaped tabs, Unicode, links and marks, source definitions, column alignment, and unchanged surrounding Markdown. Do not round-trip the whole entry through lossy TSV after an unrelated edit. Newline-to-space normalization belongs specifically to a deliberate single-line-cell paste and remains one undoable edit.

**Conditional architectural verdict:** retaining one native text view is coherent if it has actual cell-aware layout, a semantic table model independent of presentation delimiters, complete selection/edit mapping, and accessible cell navigation. It may reduce undo complexity but does not automatically solve it. Before replacing the approved attachment approach, amend the design with those concrete platform decisions and inspect a bounded prototype: a two-column table with long wrapped text, an empty cell, styled text/link, adjacent body paragraphs, largest text, VoiceOver cell navigation, IME input, and cross-cell/body undo/copy. No broad new feature scope is requested; these cases distinguish a usable native table from aligned text. If the UIKit layout/accessibility approach cannot satisfy them, retain the approved structured table attachment with native cell editors and the shared document undo coordinator.
