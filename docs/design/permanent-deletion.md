# Permanent deletion — proposal

Implements the Delete Permanently action already specified in screens.md. Requires core and sync integration before UI exposure; this document is not implementation evidence.

## Meaning and limits

Permanent deletion removes the selected content and its earlier versions from normal Journal recovery on this device. A minimal encrypted deletion marker is retained for sync ordering; synced devices remove the content from their ordinary lists/history after receiving it. The current protocol retains immutable encrypted server revisions and retry receipts. Exported archives, server history, backups, previously authorized agents and disconnected devices can retain copies. Do not promise physical or cryptographic erasure. This first implementation does not change those server-retention guarantees.

Concurrent unreviewed edits are never silently destroyed. Known conflicts block deletion and offer Review Changes. An edit arriving from another device while deletion is pending produces explicit conflict review. That review names the sides “Deleted Entry” and the actual edited entry; choices are “Keep Deletion”, “Keep Entry”, and “Keep Entry as Copy”. The last retains the original deletion marker and creates a new entry identity. A journal marker conflicting with settings uses Keep Deletion / Keep Journal; child entries are never recreated just by keeping journal metadata. All choices are deliberate; none is preselected for automatic resolution.

## Entry flow

Recently Deleted > entry > More > “Delete Permanently…”. Native destructive confirmation sheet, title “Delete Entry Permanently?”; name/date identifies the captured entry, with Untitled Entry fallback. Copy: “This entry and its earlier versions will be removed from Journal on your devices after syncing. Copies in archives and server history may remain.” Native Cancel and destructive “Delete Permanently”. Cancellation leaves content unchanged. The action operates on the exact captured version; changed content requires fresh review. No undo or Restore after a committed deletion. Other entries using the same image retain it.

## Journal flow

Recently Deleted > journal details > “Delete Permanently…”. Title “Delete Journal Permanently?”. Display captured journal name and the number of current entries included, including independently deleted entries still belonging to this journal. Copy: “This journal, its N entries, and their earlier versions will be removed from Journal on your devices after syncing. Copies in archives and server history may remain.” For zero entries use “This journal and its earlier versions…”; use singular for one. Additional secondary copy: “Entries that haven’t synced from other devices may need review later.” Entries currently moved to another journal are excluded, regardless of their history. Historical-only records without a current entry remain preserved in archives rather than inferred as current journal membership.

After a parent is permanently deleted, a previously unseen child arriving from an offline device is Unavailable, with existing explicit recover-to-another-journal actions. Never automatically delete that unseen content. A changed child set or changed affected payloads invalidates confirmation before local commit.

## Interaction, failure and accessibility

Save the current draft before confirmation and revalidate at commit. Save failure preserves the draft and exposes existing Export Entry recovery. Confirmation uses existing scrollable native sheet patterns and system styles; destructive color is supplementary to explicit text. At accessibility sizes show full multiline labels and vertical actions; standard sizes keep native Cancel/primary ordering. No custom icons, new persistent toolbar or shortened ambiguous labels.

During commit disable confirmation, cancellation and interactive dismissal; show “Deleting…” without exposing technical details. Lock before commit cancels and hides captured content. After durable commit never invite a second deletion if refresh fails: “The entry was deleted, but couldn’t be displayed. Reopen Journal to continue.” Use the journal equivalent. Missing/already-deleted records close stale confirmation without mutation. An intervening change shows “This content has changed. Review it before deleting.” with “Review Again” and Cancel. Conflicts offer “Review Changes”; unsupported content offers the existing archive export/update route rather than guessing how to rewrite it.

Success removes the entry/journal from Recently Deleted and selects the next available item or existing empty state. Journal switching, search, agent queries, archive counts and history must share marker visibility. No automatic purge or deletion timers.

## Verification gate

Before exposing actions: core exact-snapshot validation, history removal, immutable retry preservation, replay handling, explicit deletion/edit conflicts, shared-image safety and archive/import marker retention. Then native lock/save/commit failure tests and actual simulator delete/cancel/relaunch/conflict evidence at normal and largest text/dark. Inspect actual UI independently; no broad completion claim based only on core tests.

## Revision 2 — required clarifications

This section replaces conflicting copy/semantics above.

Entry confirmation copy: “This entry and its earlier versions will be removed from Journal on this device. This deletion will sync to your other connected devices. Copies may remain in archives, backups, and server history.” Separate final sentence: “You can’t undo this.” Offline or revoked devices and previously authorized agents can retain downloaded copies; the confirmation does not promise their erasure.

Journal confirmation: “This journal, the N entries currently belonging to it, and their earlier versions will be removed from Journal on this device.” Follow with the same sync, retention and no-undo sentences. Use singular and zero variants. When independent deletions are included, show “This includes entries already in Recently Deleted.” The count excludes entries currently moved elsewhere. Historical versions of those moved entries remain. If history-only entries reference the journal, show “Some earlier versions have no current entry. They aren’t included in this deletion and will remain in your archive exports.” Those history-only records remain locally stored and in future exports; no archive is automatically created. This exceptional condition must be captured alongside the confirmation before its action is enabled.

Deletion-conflict review is a distinct native sheet, not the ordinary conflict sheet with renamed buttons. Title “Review Changes”. Identify the deletion side as “Deleted Entry” (or “Deleted Journal”), with its device name and event time. Identify the edited side by title, device and event time. Use existing Unknown Device/Untitled fallbacks. Include the full supported edited document and loaded images, with normal unavailable-image indication if bytes are missing; no summary-only decision. An absent event time must say unavailable, not substitute the current time. Both reviewed revisions are captured and revalidated at the final mutation; changed input returns to review without choosing a winner.

Entry choices:

- “Keep Deletion” has nearby explanation “Removes this edited version and its earlier versions from Journal.” It opens a second destructive confirmation, “Delete Edited Entry?”, with captured title/date, retention/no-undo copy, Cancel and “Delete Permanently”. Confirming retains the original deletion marker, removes local history/conflicting edited content and queues the explicit resolution. Cancelling returns to review without changing either side. A newer conflict requires fresh review.
- “Keep Entry” has explanation “Keeps the edited entry. Earlier versions already deleted aren’t restored.” Uses the existing recovery destination selection flow, requiring a supported live conflict-free journal, even when the old parent is unavailable. It deliberately revives the original entry identity with the reviewed edited content/date/images and selected journal, clearing its deletion marker. It does not restore lost older history or silently restore the parent. The final action remains Keep Entry, and the selected destination is displayed before committing.
- “Keep Entry as Copy” has explanation “Creates a new entry and keeps the original deleted.” Uses the same explicit destination flow. It copies reviewed content/date/images under a new entry identity and leaves the original deletion marker; it does not resurrect the original history. Both records commit together locally, and retries retain their identities. Failure never creates a second copy or discards the conflict before the local transaction succeeds.

Journal metadata conflict choices are Keep Deletion (with the same second destructive confirmation) and “Keep Journal”. The latter displays “Keeps this journal’s name and template. Deleted entries aren’t restored.” It revives the journal identity as a live journal, preserving the reviewed name/default-template reference, while existing permanently deleted child markers remain deleted. Show the existing empty-journal state if none survive. Unseen offline children remain Unavailable while the parent stays permanently deleted; if the user explicitly keeps the journal, later ordinary nondeleted children may become visible there. Keeping journal metadata never manufactures or recovers child payloads. Child deletion/edit conflicts remain individually unresolved until reviewed.

Every conflict flow has native Cancel. Lock clears captured versions/destinations, cancels precommit work, and suppresses late error/preview publication. Unsupported edited content remains preserved and offers the active-sheet archive export/update route. A successful resolution followed by refresh failure closes into an explicit completed state without repeating the destructive operation. Postcommit error copy: “The entry was deleted, but Journal couldn’t update the view. Reopen Journal to continue.” Use the journal equivalent. No destructive action receives automatic initial activation.

Final reviewed clarification: the journal-metadata Keep Deletion confirmation is titled “Delete Edited Journal?” and says “Removes this edited journal’s name, template setting, and earlier versions from Journal.” Follow with the reviewed retention/no-undo sentences and Cancel / Delete Permanently actions. This confirmation does not authorize an additional child-deletion operation. The historical-only warning and its affected identity set must be captured and revalidated alongside current membership; a newly appearing excluded historical-only record requires refreshed scope review.

Reviewed surviving-history clarification: only Keep Deletion purges surviving source history, with that history captured and revalidated in the final destructive scope. Keep Entry preserves still-existing history without recreating versions already deleted. Keep Entry as Copy preserves remaining source history for lossless archive export, does not attach it to the new copy, and keeps ordinary restoration from the marked source blocked. Copy explanation: “Creates a new entry and keeps the original deleted. Any remaining earlier versions stay available in archive exports.” Images referenced by surviving payloads remain intact.

## Integration details and two-deletion conflict case

The confirmation entry point follows the current navigation refinement: entry context menu and selected-entry Entry Actions menu, only in Recently Deleted, labeled “Delete Permanently…”. Journal details in Recently Deleted use the same label after Restore/Version History. No permanent deletion appears beside ordinary writing controls. Recently Deleted help becomes “Deleted items stay here until you restore or permanently delete them.” Confirmation identity/date and journal counts come from the store-bound reviewed snapshot, not the live selection.

If both conflict sides are canonical deletion markers, there is no edited document to preview or restore. Show “Deleted Entry” or “Deleted Journal” for each event, with This Device/recorded remote device identification and event times. Copy: “Both devices deleted this entry.” (journal equivalent), followed by “Keeping the deletion also removes any remaining earlier versions from Journal.” Offer Cancel and “Keep Deletion…”, with the same separate destructive confirmation and archive/backup/server-history/no-undo disclosure. Do not offer Keep Entry, Keep Copy or Keep Journal. The second confirmation is titled “Keep Entry Deleted?” or “Keep Journal Deleted?” and identifies the available deletion event rather than inventing the lost entry title. It binds the same surviving history scope as other deletion decisions.

Unknown or unsupported marker/edited versions cannot enter the destructive screen. The generic conflict router displays an update notice and active-sheet archive export; no generic Keep Version/Keep Both controls may overwrite them. A marker whose local current record is omitted from the ordinary list remains reachable through the existing Settings conflict collection.

Reviewed provenance clarification: use “On This Device” only as storage location, not an authorship claim. Show recorded origin when known and “Unknown Device” otherwise. A missing time is “Time Unavailable”. Unless distinct authorship is established, the two-marker sentence is “Both versions show this entry as deleted.” (journal equivalent).

Implementation discovery: there is currently no global Settings conflict collection. Add a conditional “Changes to Review” section to Settings > Sync, listing unresolved record conflicts only. Each row uses the surviving edited title (Untitled Entry/Journal fallback), “Deleted Entry”/“Deleted Journal” when both versions are markers, and a “Review Changes” action opening the proper review sheet. Ordinary entry review remains available in its existing location. This section disappears when empty and gives omitted marker records a reachable review path. Use multiline native row labels; never leak preview content when locked.

Reviewed implementation refinements: duplicate journal names remain selectable. Show recorded creation date to distinguish them, and only for remaining name/date collisions append an abbreviated unique record-ID prefix. Use the same label in the selected destination and accessibility description. Rejected destinations offer Reload Journals, which refreshes the list after pending saves settle and requires a fresh deliberate choice. At accessibility sizes, repeat the complete destructive question as a wrapping heading in the scrollable content so the inline navigation title cannot hide it. Remove the raw device-ID disclosure; use truthful Unknown Device provenance when a name is unavailable.
