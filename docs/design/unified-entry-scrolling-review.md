# Unified iOS entry scrolling: independent proposal review

## Verdict and evidence

The single scrolling writing surface is the appropriate design direction. Implementation approval awaits the bounded clarifications below. Read `unified-entry-scrolling.md`, the rotation measurement text attachments, and current header, title editor, native body editor, and RootView integration. No production files were changed and no reviewer tests were run.

The measurements support the proposed change: landscape navigation ends at 78 points and the body viewport ends at 194, leaving 116 points. The measured title alone is 69.33 points, while the existing body viewport is 56. Dividing this region cannot fully display both. Allowing earlier title/header content to scroll naturally away follows familiar document editing behavior and preserves system text sizing. Keeping the existing native body view as the input, selection, and undo owner avoids unnecessary risk to rich text. No new copy or persistent controls are needed.

## Required proposal clarifications

### Native accessibility exposure

An accessible UITextView may suppress traversal into its hosted header. The proposal currently says to check exposure but does not describe a mechanism. The parent's follow-up offers a suitable concrete direction: a non-accessible wrapper container explicitly exposes the hosted header followed by the actual native UITextView. Record this in the proposal. Preserve individually accessible title/notices/buttons and the body's native editable-text semantics; do not substitute a plain text proxy or disable body accessibility to expose the header. Avoid duplicate elements or accessibility-container cycles.

Verify this structure early using the native accessibility tree: complete header controls, their hittability/activation, and the real editable body must remain discoverable. A successful XCTest query is necessary bounded evidence, not a claim of VoiceOver reading order or editing acceptance. If the explicit ordering cannot expose the hosted header reliably, stop and revise the hosting arrangement before completing the integration.

### Focus and scroll precedence

Specify distinct policies for the active title, active body, and passive reading. While the title owns focus, keyboard/rotation/header layout should reveal the title insertion region; an old body selection must not pull the viewport away. Next transfers focus to the same body view and reveals its current selection. While the body owns focus, reveal the active line/caret above the complete predictive keyboard. Passive readers should retain a visible body anchor when header height changes. Preserve existing text selection and do not reset the editor merely to reveal it.

Make save-failure reveal a one-shot request after the alert dismisses, tied to the current entry and vault session. Explicit failure reveal takes precedence over body-anchor compensation. Do not repeatedly pull users back to the warning while typing, rerendering, or retrying; discard stale pending reveals when entry/session changes. No accessibility focus action should compete with the modal alert. Ordinary header changes, including disappearance of a successful retry notice, preserve the current reading/writing position as far as scroll bounds permit.

### Stable hosting and empty-body presentation

Update one stable hosting view and header identity for the current entry. Replacing its content on every body keystroke must not recreate the title responder or cancel/restart a notice's owned retry task. Scope asynchronous measurement/reveal callbacks to the current entry/session and ignore obsolete results. Preserve the existing coordinator/JournalTextView APIs and optional-header behavior used by focused tests, as requested by the parent.

Move the existing “Start writing…” placeholder with the body's text-container origin. RootView currently overlays it at the top of the native editor; leaving it there would overlap the hosted header once the editor owns the whole surface. Keep it noninteractive and hidden from accessibility as currently intended, with unchanged copy. Retain the current horizontal alignment deliberately; fitting the header to the body width must not accidentally apply both outer editor padding and old header padding twice.

## Implementation cautions and acceptance

Measure at the actual available width and respond to Dynamic Type, keyboard, appearance, and notice changes without replacing attributedText for a height-only change. Prevent recursive layout/inset updates by applying only meaningful measured changes. Anchor compensation must use actual adjusted scroll bounds, with clamping at the start/end, and must not counteract a drag/deceleration or explicit focus/reveal request. Header-height changes and width-driven image reflow should cooperate rather than each applying the other's offset adjustment again. The current image-anchor code already uses `textContainerInset.top`, so inspect that interaction explicitly.

Keep the existing title editor and body document separate: Select All/Copy in the body should not suddenly include title/notices, and title editing must not alter the rich-body document. Scrolling gestures beginning on the hosted header should scroll the same surface without creating a second scroll region or breaking title selection and native edit menus.

The proposed focused acceptance routes are appropriate: normal/largest rotation with typing continuation, explicit full-title reveal and return to body, retry-notice boundary, multiline-title Next, selection/undo, and image viewport preservation. Include the empty-body placement and native header/body accessibility exposure. Capture the active line/caret relative to the full predictive keyboard, not solely its narrower accessibility frame. Inspect the return from title/header to continued body typing and a header-height change while the body is scrolled. Reuse focused existing tests where meaningful; no broad unrelated reruns are requested.

Mac remains outside this layout change. Phone screenshots and text persistence do not establish iPad, VoiceOver, IME composition, arbitrary long-title behavior, physical-device installation, or preservation of drafts under failed storage writes. A new archive should follow source and actual-UI acceptance rather than the current proposal review alone.

## Initial integration source review

Inspected `JournalWritingView`, iOS `NativeEditor` integration, uncapped `EntryHeaderView`, `TitleTextView` insertion reveal, and RootView's shared editor construction/placeholder migration. The wrapper explicitly exposes the existing hosted header and real body view, retains one hosting view, measures its content height into the body inset, and excludes the placeholder from accessibility. Header geometry changes do not directly replace attributedText. The Mac header and placeholder remain on the existing path. These choices follow the approved design; they do not by themselves prove host-state preservation or accessibility reading order.

Two concrete source corrections remain:

1. `layoutHeader()` gates title/body insertion visibility on header height or width changes only. A keyboard appearance/disappearance or other viewport-height-only change can obscure the focused insertion without changing either header dimension. A title's begin-editing reveal may run before the keyboard settles; subsequent height changes currently skip this correction. Track usable viewport size/inset changes as well and apply the reviewed title/body focus precedence when that region changes.
2. Automatic caret reveal and passive offset compensation do not account for `isTracking`, `isDragging`, or `isDecelerating`. A header resize during a user scroll can pull the view back to the insertion or change its offset against the gesture. Defer automatic corrections during user scrolling, except the explicitly prioritized one-shot failure request. Preserve the appropriate anchor when resuming and clamp offsets to valid adjusted scroll bounds.

Also keep an explicit failure reveal authoritative through its header measurement/layout settling. The current flag is consumed on the first layout; a later changed header height can immediately invoke active-body reveal instead. Verify the immediate post-dismissal notice remains visible after layout settles, rather than relying only on the first offset assignment. Avoid retaining that priority indefinitely after the user deliberately resumes writing or scrolling.

The new UILabel placeholder is single-line by default; inspect its full copy at large text and constrained widths, preserving the prior natural wrapping if needed. The title-selection callbacks and hosted header gestures also need actual native checks: source alone cannot prove that scrolling begins correctly over the title or that repeated hosting configuration updates preserve the title responder and retry task.

## Follow-up source review: viewport and failure ownership

Re-inspected the revised `JournalWritingView` and title/body interaction callbacks. Height and adjusted-inset changes now participate in viewport change detection. Automatic layout-driven insertion reveal and passive compensation are suppressed during tracking, dragging, and deceleration. Failure reveal pins its priority across subsequent layout changes until interaction or failure clearance; entry changes reset its state. The new callbacks are correctly confined to the iOS `JournalTextView` and its coordinator/title integration. These address the main previously reported source gaps.

Two small corrections remain before source approval:

- When `configure` receives `failure == false`, it clears `failurePinned` but retains a previously queued `revealFailure`. If saving recovers before the requested layout runs, that stale request can still scroll the surface to the top. Clear both pending and pinned failure state when no revealable failure remains. An explicit user interaction superseding a queued reveal should likewise clear the queued request.
- Passive header-height compensation still calls `setContentOffset` with an unbounded target. Clamp to the actual adjusted scroll range after the inset/content layout is updated: from negative adjusted top inset to the greater of that minimum and content height minus viewport height plus adjusted bottom inset. This matters when a tall notice disappears near the end of the body. Do not add a forced caret jump after a deliberate user scroll merely to compensate for an update that occurred during the gesture.

The gesture code suppresses adjustments while scrolling; it does not implement a stored deferred anchor. Verify passive reading through a header-height change in the focused acceptance route rather than claiming deferred-anchor behavior from this source. The existing placeholder wrapping and hosting-state evidence limits also remain.
