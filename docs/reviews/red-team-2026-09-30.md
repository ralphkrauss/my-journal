# Red-team inventory, 30 September 2026

Six attackers each covered one area: server, agent access (MCP/OAuth), sync, iPhone, iPad and Mac. An independent verifier re-ran every finding. Only findings the verifier confirmed are in the main list; the rest are in the appendix. Severities are the verifier's.

On 1 October I checked each confirmed finding against the current source tree, because other work changed the code during the run. The **Status** column shows the result: *Open*, *Fixed in tree* (the code now addresses it; re-test on the next build) or *Superseded* (a later owner decision changed the behaviour). Fixes were confirmed by reading the code only. Nothing was re-run.

## 1. Summary

**29 confirmed findings:** 2 high, 6 medium, 21 low.

| Server | 0 | 0 | 1 | 1 | 0 |
| MCP / OAuth | 0 | 0 | 2 | 2 | 0 |

Six findings are already fixed in the tree: SRV-01, AMO-1, AMO-2, IPH-2, IPH-3 and IPH-10. Three were superseded by owner decisions made on 30 September: IPH-1 (empty entries are now kept) and IPH-4 and IPH-5 (App Lock no longer has its own PIN). One more report was a documented design choice and is in the appendix (AMO-3).

The server and agent access held up well. No one got past setup, device credentials, OAuth, the per-grant data boundary or the container hardening. All the serious problems are in the clients' sync logic, around **Turn On Encryption** and revision bookkeeping.

**What to fix first:**

1. **SYNC-2:** a sync pass already in flight while encryption is turned on can upload readable journal text to the newly encrypted server and break sync on every device. It breaks the privacy promise, and the fix is cheap.
2. **SYNC-1:** if the other device signs in before the upgrading device has finished uploading, the upgrading device hides the whole journal behind reviews of identical text, and its image entries stop syncing for good. This is likely on libraries with many images.
3. **SYNC-4 and SYNC-5 (one fix):** `Store.apply` ignores a remote change that has the same revision number but different content. After a server rollback, or after resolving a review while a push is in flight, devices disagree silently or an entry never syncs again.
4. **IPAD-1:** while typing on iPad, an invisible strip above the keyboard swallows taps on the entries list.
5. **MAC-1:** the Import Archive panel survives App Lock and can open a sheet with no buttons over the lock screen. It is a one-line fix.

Next come SYNC-3 (two merges of twin libraries overwrite an edit), IPAD-2 (rotating draws an entry cut off) and a batch of cheap polish fixes. SYNC-6, how a review shows a move or delete, needs an owner decision and the design gate.

## 3. Findings in detail

Evidence paths under `scratchpad/` refer to the reviewing session's temporary scratchpad, which is not part of the repository. The sync reproductions are XCTest cases in a scratch copy of JournalCore that ran against disposable servers.

### Sync

#### SYNC-2: A sync pass in flight across Turn On Encryption uploads plaintext (High, Open)

- **Steps:**
  1. Start with an unencrypted vault where device A has an entry containing a canary string and is synced.
  2. Turn on encryption (`encrypt()`: sync, `syncedPosition`, `reencryptedCopy(.restart)`).
  3. Have an automatic sync pass of the old plaintext library already waiting on the store's sync gate, so that its page request lands just after `POST /v1/recovery/encrypt`.
  4. Let the old pass finish. Then sync the encrypted copy A2, and sign in a new device C.
  5. Reproduction: `EncryptionInFlightSyncTests.testSyncInFlightDuringSwitch`.
- **Expected:** a plaintext library never writes to a server that has switched to encryption (enable-encryption.md: "A device still in plaintext mode must never push plaintext into the encrypted vault").
- **Actual:**
  - The old pass gets `server_changed`, reconciles against the new identity and re-uploads every record as readable JSON. The server accepts it, because its only check is a minimum length.
  - A2 and C then fail every sync with `authenticationFailure`, and there is no recovery in the app.
- **Evidence:** "server records: 2 readable with canary: 1"; A2 and C both show `authenticationFailure`.
- **Cause:**
  - `synchronizeBeforeEncrypting` releases the sync gate before `pauseWriting(true)`, and `pauseWriting` only stops new `AppModel.sync` calls.
  - `SyncEngine.synchronizeAgainIfServerChanged` plus `SyncReconciliation.reconcileMissing` then requeue plaintext.
  - Files: `apps/apple/JournalApp/Model/EncryptionOperations.swift`, `SyncEngine.swift`.
- **Fix:**
  - Hold the store's sync gate from before the switch request until `openReplacedLibrary` has replaced the library.
  - In `SyncEngine`, refuse to reconcile or push when the server reports an encrypted format but the store is `.plaintext`, and treat that like unauthorized.

#### SYNC-1: Other device signs in before the upgrading device has uploaded (High, Open)

- **Steps:**
  1. Start with devices A and B synced on an unencrypted vault, with an entry containing an image.
  2. A turns on encryption, but its encrypted copy A2 hasn't uploaded yet.
  3. B signs in with the new password, re-encrypts with `.reconcile` and uploads everything first.
  4. A2 then syncs. Resolve its reviews and edit the image entry's title.
  5. Reproduction: `EncryptionTransitionTests.testRejoinBeforeUpgraderUploads`.
- **Expected:** A2 recognizes that B's records and images decrypt to the same content and adopts them without reviews.
- **Actual:**
  - Three reviews with identical text appear (journal, entry, entry).
  - With the journal in review, all its entries become `unavailable(.conflict)`, so the journal disappears on A2.
  - Every image upload gets `409 attachment_is_immutable`, and the message "Your server didn't accept an image…" persists after Sync Now and relaunch.
  - After the reviews are resolved, A2's title edit stays pending forever.
- **Evidence:** the test output above. The verifier reproduced it exactly.
- **Cause:**
  - `StoreReencryption.restart` sets images to `uploaded = 0` (line 241), not the verify state 2 that the join flow uses.
  - `Store.apply`/`recordConflict` never compares decrypted content.
  - `SyncEngine.uploadImages` and `ServerClient.upload` treat 409 as a permanent rejection.
- **Fix:**
  - Mark images `uploaded = 2` (verify) in `restart`.
  - When a push conflict's remote payload decrypts to the same content, adopt the remote revision instead of recording a review.
  - On 409 for an image, download it and acknowledge it if it decrypts to the same bytes.

#### SYNC-4: Lost acknowledged write leads to silent disagreement (Medium, Open; fix with SYNC-5)

- **Steps:**
  1. Sync A and B, then snapshot the server's data folder.
  2. A edits and pushes; the push is accepted, but the following page read fails.
  3. Restore the snapshot (same server identity).
  4. B edits the same entry and pushes at the same revision number.
  5. Sync both twice, and add a new device C.
  6. Reproduction: `RollbackTests.testLostAcknowledgedWriteWithoutPull`.
- **Expected:** continuity detects the rollback, or the same revision with different content becomes a review (architecture.md says such rollbacks are detected).
- **Actual:** A keeps "written on A" with nothing pending and no review. B and C show "written on B". A's next edit will silently overwrite B's version.
- **Evidence:** "A pushes: 1 pending after: false"; "A current: written on A … conflicts: 0"; "New device C sees: written on B".
- **Cause:**
  - `Store.swift:533`, `if trustingRevision && change.revision <= revision { return }`.
  - The continuity check confirms only the last pulled cursor, not acknowledged pushes.
- **Fix:** in `apply`, when an incoming change has the same revision but a different payload (and isn't this device's own acknowledged payload), record a review or start reconciliation. Alternatively, include the last push receipt in the continuity check.

#### SYNC-5: Resolving a review while its push is in flight (Low, Open; fix with SYNC-4)

- **Steps:**
  1. Edit entry E to "A1" on A. While that push is in flight, a stale save from a second window creates a review.
  2. Choose Keep Version from This Device.
  3. The push of "A1" is then acknowledged at revision 2.
  4. Edit E again and run Sync Now 3 times.
  5. Reproduction: `RetryTests.testSaveAndResolveDuringPush`.
- **Expected:** the resolved version and later edits reach the server, or a problem is shown.
- **Actual:**
  - The queued op with base 1 gets `revision_conflict` on every pass, and the conflict is dropped by the same early return in `apply`.
  - A shows pending forever with no message, and other devices keep "A1".
- **Cause:**
  - `Store.acknowledge` (lines 485–500) re-enqueues with `INSERT OR IGNORE`, which is ignored because the resolve's op exists.
  - `apply` then returns early. `resolveDeletionConflict` (StoreDeletion.swift:117–126) has the same pattern.
- **Fix:** in `acknowledge`, rebase an already-queued op: set its base to the acknowledged revision, or delete it if its payload is equal. Treat a push conflict whose remote revision is ≤ the local revision as a signal to rebase.

#### SYNC-3: Twin local libraries merged into one server (Medium, Open)

- **Steps:**
  1. Give two phones the same local library (Restore Archive into an empty device recreates identities).
  2. Edit the same entry differently on each.
  3. Both phones join one server with Merge.
  4. Reproduction: `MergeTwinTests.testTwinLibrariesMerge`.
- **Expected:** the two edits become a review, or both are kept.
- **Actual:** all three devices show only the second phone's text, with 0 reviews. The first phone's text survives only in that phone's local Version History.
- **Cause:** `StoreMerge.importMerged` (StoreMerge.swift:108) saves differing content at revision ≤ 1 as an ordinary edit, on the assumption in join-with-local-journals.md §2.1 that "only the earlier attempt wrote it".
- **Fix:** keep differing content at revision 1 for review unless this device can prove it sent that version. For example, persist the identities and payload digests an earlier merge attempt pushed, and compare against them.

#### SYNC-6: Review hides moves and deletes (Low, Open; owner decision)

- **Steps:**
  1. A moves one entry to Home and another to Recently Deleted.
  2. B edits both entries offline and syncs, which creates 2 reviews.
  3. Choose Keep Both.
  4. Reproduction: `MetadataConflictTests.testMetadataChangesInReview`.
- **Expected:** the review shows when a version is in another journal, in Recently Deleted or has a different date.
- **Actual:**
  - Only the title, the modified date and the text are shown.
  - Keep Both brings the edited copies back to Work, which undoes the move and the delete. Old-text copies sit in Home and in Recently Deleted.
  - Nothing is lost.
- **Cause:** `apps/apple/JournalApp/Views/EntryConflictReview.swift:44–53`. This matches the approved accessibility design, which doesn't address location. Journal reviews already show Location.
- **Fix:** add one line per version when its journal, deleted state or date differs (for example "In Home" or "In Recently Deleted"). This goes through the design gate.

#### SYNC-7: Clock set back holds automatic sync (Low, Open)

- **Steps:** save an edit, then run automatic sync passes with the clock 1 hour earlier, stepping forward 10 minutes per pass. Reproduction: `ClockTests.testClockSetBackHoldsAutomaticSync`.
- **Expected:** the 2 s pause and 30 s longest wait still apply.
- **Actual:** not sent within 50 minutes of clock time. Leaving the entry, backgrounding or Sync Now still send it.
- **Cause:** `SyncReconciliation.isBeingWritten` (line 305) treats negative intervals as "still writing". `StoreCheckpoints.hasElapsed` doesn't.
- **Fix:** treat negative elapsed time as elapsed.

### iPad

#### IPAD-1: Invisible band above the keyboard swallows taps (Medium, Open)

- **Steps:**
  1. iPad in portrait, journal with 7 or more entries; focus an entry body.
  2. Tap a list row at the height of the Aa / Image / Source pill (y≈780–823 pt).
- **Expected:** only the pill takes touches.
- **Actual:** taps in a strip about 56 pt tall across the whole width do nothing. The same row 40 pt higher works.
- **Evidence:** `scratchpad/redteam/ipad/evidence/accessory-band-blocks-list.png`, `scratchpad/redteam/verify-ipad/evidence/band-tap-ignored.png`.
- **Cause:** `apps/apple/JournalApp/Editor/WritingAccessory.swift:7–25`. It is a full-width `UIInputView` with a clear hosting view and no hit-test override.
- **Fix:** override `point(inside:with:)` so it returns true only inside the pill. Also check hardware-keyboard mode, where the bar may cover the list's New Entry button.

#### IPAD-2: Rotation draws a template entry cut off (Medium, Open)

- **Steps:** in portrait, New Entry → use a template → Weekly Reflection, tap the body, tap Done (✓), rotate to landscape.
- **Expected:** all three headings are drawn.
- **Actual:** the third heading is cut through its middle and nothing is drawn below it. The text view's frame and value are complete, so no text is lost. Opening another entry and coming back fixes it. Reproduced 9 of 9 times across both runs.
- **Evidence:** `scratchpad/redteam/ipad/evidence/landscape-clipped-template-entry.png`, `scratchpad/redteam/verify-ipad/evidence/landscape-clipped.png`.
- **Cause (unconfirmed):** `JournalWritingView.layoutHeader` (lines 120–160) changes the inset and offset during rotation without forcing a new layout and redraw.
- **Fix:** after an inset or width change, invalidate the layout and redraw. Add one UI check for this sequence.

#### IPAD-3: Add Link doesn't focus the Link field (Low, Open)

- **Steps:** with the body focused, tap Aa → Insert → Link….
- **Expected:** the Link field has focus with the keyboard up, as on the Mac.
- **Actual:** no field has focus and no keyboard appears. The verifier also saw this with ⌘K, while the attacker saw ⌘K work, so check both paths on a real iPad.
- **Evidence:** `scratchpad/redteam/verify-ipad/evidence/add-link-unfocused.png`.
- **Cause:** `FormattingPopover.swift:146–152` with `EditorActions.finishPresentation` (RichText.swift:160–175). The sheet's `onAppear` focus probably loses to the popover's dismissal.
- **Fix:** set focus after presentation has settled, or present only after the popover has finished dismissing.

#### IPAD-4: Format panel survives widening the window (Low, Open)

- **Steps:** in iPadOS 26 windowed mode, narrow the window to compact width, open Aa (the Format panel replaces the keyboard), then widen the window to regular width.
- **Expected:** the panel closes and the keyboard returns (menus-and-popovers.md D6).
- **Actual:** the panel stays. Tapping Aa recovers.
- **Evidence:** `scratchpad/redteam/ipad/evidence/format-panel-stays-after-widening.png`.
- **Cause:** `MobileFormattingPresenter.swift:33–44` only overrides `willTransition(to:with:)`, which windowed resizing doesn't call.
- **Fix:** also observe horizontal size-class trait changes (`registerForTraitChanges`).

### iPhone

#### IPH-6: Caret line hidden after inserting a photo (Low, Open)

- **Steps:** put the caret at the start of a body, then Insert Image → Photo Library and pick a photo.
- **Expected:** the caret line is fully visible above the toolbar (unified-entry-scrolling.md).
- **Actual:** the caret line stays half behind the Aa bar until the person types or scrolls. It depends on the caret's position.
- **Evidence:** `scratchpad/redteam/iphone/evidence/image-insert-caret-under-toolbar.png`, `scratchpad/redteam/verify-iphone/evidence/iph6-caret-under-toolbar.png`.

- **Fix:** once the image has laid out, reveal the selection with the toolbar and keyboard inset.

#### IPH-7: Version History out of time order (Low, Open)

- **Steps:** resolve a review with Keep Version from Other Device where the other version is older, then open Version History and look at the picker.
- **Expected:** newest first.
- **Actual:** "20:16:54 · 1", "20:18:07 · 2", "20:12:16 · 3". The rows are in insertion order, while the labels show modified times.
- **Cause:** `Store.history(for:)` uses `ORDER BY id DESC` (Store.swift:766), and `Store.resolve` inserts local before remote. `VersionHistoryView` doesn't re-sort.
- **Fix:** sort by `modifiedAt` descending with `id` as the tie-breaker, and show the ordinal only for equal timestamps.

#### IPH-8: Back on the trailing side in Start a Journal (Low, Open)

- **Steps:** on a fresh install, Start a Journal → Use Encryption.
- **Expected:** back navigation on the leading side and Create trailing, as in the Connect flow.
- **Actual:** Cancel is on the left, with Back and Create side by side on the right.
- **Evidence:** `scratchpad/redteam/iphone/evidence/create-journal-back-trailing.png`.
- **Cause:** `CreateJournalView.swift:68`, a `ToolbarItem` with no placement.
- **Fix:** push the step so it gets the system back button, or place Back at `.topBarLeading` and hide Cancel while Back is shown.

#### IPH-9: Pasted rich text (Low, Open; partly an owner decision)

- **Steps:** paste HTML that contains a link, a heading, lists, a table, a quote and code into a body, then open View Source.
- **Expected:** links without an underline, and supported blocks kept (notes-alignment-revision.md: "rich/structured paste preserves supported blocks").
- **Actual:**

- **Cause:** `InsertedText.ownAttributes` (InsertedText.swift:182–201) keeps the system's link underline as the person's own underline and maps only run attributes.
- **Fix:**
  - Now: drop underline on runs that carry `.link`.
  - Owner decision: whether to map pasted lists, headings, quotes and code to the app's blocks. The notes-alignment doc suggests yes.

### Mac

#### MAC-1: Import Archive panel survives App Lock (Low, Open)

- **Steps:** with App Lock on, choose File ▸ Import Archive…, then lock (⌃⌘L, or lock the screen) and pick a file.
- **Expected:** locking closes the panel, as it closes every other presentation.
- **Actual:**
  - After locking, `archiveImportRequested` is still true and the `NSOpenPanel` is still attached.
  - Picking a file shows ArchiveImportView's locked state: a sheet with no buttons that covers Unlock. Escape or ⌘. dismisses it, but a mouse-only user has no visible way out.
- **Evidence:** `scratchpad/redteam/mac/evidence/archive-import-while-locked.png`, `RedTeamMacTests.swift`, and `scratchpad/redteam/verify-mac/evidence/`.
- **Cause:**
  - The lock handler at `RootView.swift:148–169` doesn't reset `model.archiveImportRequested`.
  - The `fileImporter` completion (line 119) has no lock check, while `onOpenURL` refuses when locked.
- **Fix:**
  - Clear `archiveImportRequested` on lock.
  - Ignore the importer's result when `locked || replacingVault`.
  - Optionally give the locked state a Cancel button.

#### MAC-2: Stale click-guard state (Low, Open)

- **Steps:** click Formatting while it is disabled, or press its button and drag off. Then activate it from the keyboard or VoiceOver.
- **Expected:** keyboard activation always opens the popover and moves focus into it (menus-and-popovers.md D1).
- **Actual:** after a click on the disabled button, the popover opens without focus. After a drag-off, the first keyboard activation does nothing.
- **Evidence:** `scratchpad/redteam/mac/evidence/popover-guard-harness.swift`, `scratchpad/redteam/verify-mac/evidence/harness-output.txt`.
- **Cause:** `MacFormattingButton.swift:135` (`PopoverButton.mouseDown` always reports the click) with `PopoverClickGuard.swift`.
- **Fix:** ignore mouse-downs while the button is disabled, and clear the recorded click when tracking ends without an action.

#### MAC-3: Zoom In ignores ⌘= (Low, Open)

- **Steps:** press ⌘= on a US keyboard.
- **Expected:** Zoom In. owner-decisions-2026-09-25-review.md says to bind both ⌘= and ⌘+.
- **Actual:** nothing happens; only ⇧⌘= and keypad + work.
- **Cause:** `AppCommands.swift:54`, `.keyboardShortcut("+")`.
- **Fix:** add a hidden alternate for ⌘= and keep ⌘+ as the displayed shortcut.

#### MAC-4: "Search " for an untitled journal (Low, Open)

- **Steps:** open a journal with an empty title (one synced or restored without a name).
- **Expected:** "Search Untitled Journal".
- **Actual:** "Search " as the placeholder, the tooltip and the VoiceOver label.
- **Cause:** `RootView+Toolbar.swift:15` uses `?? "Journal"`, which doesn't catch an empty string.
- **Fix:** use the same empty-title fallback as the window title.

### Server and MCP

#### SRV-01: Duplicate audit EventIds (Low, Fixed in tree)

- **Actual (at test time):** EventIds 30–32 were used for both agent and encryption events in `Security/AuditLog.cs`, which mixed them in alerting keyed on EventId.
- **Status:** the encryption events now use 40–42.

#### AMO-1: search_entries memory (Low, Fixed in tree)

- **Actual (at test time):**
  - `McpTools.Search` held every match (up to about 32 KB each) before paging, and decrypted the copy twice.
  - With a copy near its quota and a 256 MB heap cap, one of two concurrent calls threw `OutOfMemoryException`. The server stayed up.
- **Status:** a bounded heap of offset + limit matches is now in `McpTools`. Check that the shared-journal set is built in the same pass, with no second full decrypt.

#### AMO-2: DCR redirect URIs with userinfo (Low, Fixed in tree)

- **Actual (at test time):** `https://legit.example@evil.example/cb` was registered with 201. The owner-facing view showed the real host, so this was hardening only.
- **Status:** `OAuthRedirects.Classify` now rejects userinfo (OAuthClients.cs:41). This covers redirect URIs in metadata documents too.
