# Add device (Windows)

The connected PC lets a new device join: by showing a QR code a phone or tablet scans, or by taking the nine-digit code a new device shows and comparing check codes. Behaviour and copy keys are the spec's [Add Device](../../../screens/add-device.md); both sides together are the [pair-device flow](../flows/pair-device.md). The dialog patterns are in [settings](settings.md#dialog-patterns).

## Controls

A `ContentDialog`, `Title` `settings.addDevice.title`, `ContentDialogMaxWidth` 640 epx, with a `Frame` whose pages are the states below. A PC can always show the QR code (it is a computer, like the Mac) and never needs a camera to add a device.

| Page | Content | Buttons |
| --- | --- | --- |
| Preparing | A `ProgressRing` while the server is asked whether it takes scanned codes | Close `common.cancel` |
| Showing a code | See below | Primary `settings.addDevice.showNewCode` only once expired; Close `common.cancel` |
| Entering a code | `TextBox`, `Header` `settings.addDevice.codeField`, `PlaceholderText` `settings.addDevice.codePlaceholder`, `InputScope` Number, Cascadia Mono; digits are grouped in threes as typed (the handler re-formats, keeps the caret and accepts pasted digits with or without spaces or dashes); footer `settings.addDevice.codeFooter`. Connected through HTTPS: a value row `common.serverAddress` with the full address (selectable) and a `Button` `settings.addDevice.copyAddress` (a plain copy). Through plain HTTP: `settings.addDevice.httpOnly` in secondary text instead | Primary `common.continue`, default, disabled when empty or busy, with a `ProgressRing` while looking up; Close `common.cancel` |
| Waiting for the new device | `ProgressRing` and `settings.addDevice.waitingFor`; hidden after an error | Primary `common.tryAgain` after an error with a typed code; Close `common.cancel` |
| Confirming, scanned code | Heading `settings.addDevice.addQuestion` (level 2), `settings.addDevice.addDetail` | Primary `settings.addDevice.add`; Close `settings.addDevice.dontAdd`; no default button; Ctrl+Enter |
| Confirming, typed code | Heading `settings.addDevice.checkQuestion`, the check code (six digits in groups of three, Cascadia Mono 32 epx, named `settings.connect.checkCode.label`, read digit by digit), `settings.addDevice.checkDetail` | Primary `settings.addDevice.approve`; Close `common.cancel`; no default button; Ctrl+Enter |
| Finished | The error row; nothing more can be done | Close `common.done`, the default button |
| Locked | Not shown: locking closes the dialog and declines what is waiting (best effort) | |

Any error is an `InfoBar` (Error) at the end of the content. While approving, a `ProgressRing` replaces the primary button's label and Close is disabled ([Dialog patterns, 3](settings.md#dialog-patterns)).

### Showing a code

1. A centred block: a notice when one applies (`settings.addDevice.stoppedConnecting`, an Informational `InfoBar` in `Caption` size); the QR code; `settings.addDevice.scanInstructions`; a status line: a `ProgressRing` and `settings.addDevice.waiting`, or after three failed checks in a row `settings.addDevice.unreachable`; once expired `settings.addDevice.expired` in place of the QR code and no status.
2. A value row `settings.connect.server` and the server's host (selectable), so the person can tell that the new device's Merge page names the same server.
3. A [navigation-style](settings.md#card-patterns) row with a `HyperlinkButton` `settings.addDevice.enterCodeInstead` and its footer `settings.addDevice.enterCodeInstead.footer`; it stops showing codes and shows the code field.

**The QR code.** Generated by a small QR library from the invite the spec defines, rendered into a `WriteableBitmap` as black modules on a white `Border` with a four-module quiet margin and rounded corners (8 epx), 220 epx plus the margin, at least 200 epx at any text size. It does not scale with text size and is never inverted in dark mode or a contrast theme ([platform.md, 29](../platform.md#29-qr-codes-and-add-device), [21](../platform.md#21-theming-and-contrast)). It is one `Image` with `AutomationProperties.Name` `settings.addDevice.qrLabel`.

- While the window is not active (`Window.Activated` deactivated, another window in front) a plain placeholder tile of the same size replaces it, and the code is dropped; a new one appears when the window is active again. This is the spec's rule for "the app isn't active" (open-questions A32 asks whether it should apply to a window that is merely behind another).
- The code changes every two minutes; the one it replaced is still watched for 30 seconds; the session lasts ten minutes. The server is asked every four seconds.
- **Capture exclusion.** While a code is visible (and while the check code is shown) the library window is excluded from screenshots, screen sharing and Recall with `SetWindowDisplayAffinity` (the constant of [platform.md, 20](../platform.md#20-screen-capture-and-window-privacy)), whatever the D28 setting says, and the previous state is restored when the dialog closes. The spec excludes the sheet's window because its code lets a device join; the Windows dialog lives in the library window, so the whole window is excluded for that time. It blocks the person's own screenshot too, which is why it is only for this dialog.

## The approval

Approve and Add device ask for the device owner first ([Windows Hello](../flows/app-lock.md), [the gate](settings.md#the-authentication-gate)), always, whether or not App Lock is on, with the reason `settings.addDevice.authReason` (capitalised) and the device's cleaned name. A PC without Windows Hello continues without it. Cancelled or failed Windows Hello: nothing is said; the dialog stays on the confirmation. After Windows Hello answers, focus returns to the primary button.

**Scanned approval without a click.** The spec lets a scanned request go straight to authentication when authenticating is itself a deliberate act and no screen reader runs. A Windows PC cannot know before the prompt whether Windows Hello will use a face (no deliberate act), a fingerprint or a PIN. So on Windows a verified scanned request always waits for the person to choose Add device, as the spec does for Face ID and VoiceOver. Reason: never approve without a deliberate act.

The device's name is shown cleaned as the spec says (control and direction characters removed, trimmed, `settings.addDevice.newDevice` when empty, at most 60 characters: 59 and "…"), in plain text.

## Accessibility

- The QR code is one image named `settings.addDevice.qrLabel`; the instruction text beside it is the usable alternative, and Enter code instead is one Tab away. The check code is read digit by digit, and is also announced (`settings.connect.checkCode.announcement` is for the new device; here the heading `settings.addDevice.checkQuestion` is the prompt).
- Status changes (`settings.addDevice.waiting`, `settings.addDevice.unreachable`, a new device waiting) are announced by notification events (`MostRecent`); the incomplete-code error is announced and shown.
- Focus: Preparing keeps focus on the dialog; the code field takes focus on Entering a code; the primary button takes focus on the confirmation (not the Add button by accident: focus lands on the heading first, then Tab).
- Approve and Add device use Ctrl+Enter so Enter alone cannot approve; Narrator reads the accelerator.
- Contrast themes: the QR tile stays black on white; the tile has a visible border in contrast themes.

## Different by design

- **Windows Hello** replaces Face ID, Touch ID and the passcode.
- **Capture exclusion of the whole window** while a code shows, because dialogs are in the window.
- **Always choose Add device first.** Apple auto-starts authentication only for deliberate methods; Windows cannot know the method in advance.
- **The QR code needs no camera on this PC** and is shown by every Windows PC: this PC is the approving side; only a phone or tablet scans it.
- **Keep the display on, as the phone does.** While a code is shown (at most ten minutes) the dialog holds a `DisplayRequest` so the screen does not dim or lock before the new device scans; it is released when the dialog closes. The spec does this on iPhone and iPad only; a PC's screen also dims, sleeps and locks while its person waits for a phone, so Windows does it too.
