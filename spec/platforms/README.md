# Platforms

The spec in the folder above says what My Journal does. Each folder here says how one platform does it: which controls, layout, gestures and shortcuts present a screen or flow, where the platform's own words or conventions differ from the spec and why, which source files implement it, and what it looks like. Together with the spec, a platform folder lets an agent on another operating system port any feature without running the original client, because the controls are named, the source files are listed and the screenshots are in the repository.

| Folder | Platform | Pages are called | State |
| --- | --- | --- | --- |
| [apple/](apple/README.md) | iPhone, iPad and Mac, SwiftUI and AppKit | Implementation notes | Shipped; the notes are written from the source and the running apps, with captured screenshots |
| [windows/](windows/README.md) | Windows 11, WinUI 3 and the Windows App SDK | Mapping files | Proposals, reviewed in part; implementation not started |
| `android/` | Android | not started | Not started; see Adding a platform |

No platform is the reference for everything. A feature's reference is the platform that shipped it first (`reference:` in [parity.yaml](../parity.yaml)): when you port a feature, read the spec, then that platform's page for it, then your own platform's page. A feature can start on any platform; the originating platform's page and screenshots are written in the same change as its code ([spec/README.md](../README.md), Spec-first workflow).

## What a platform folder contains

Every platform folder has the same shape, because screens and flows can share an id (`connect-to-server`), so the folders mirror the spec's:

| Path | Contents |
| --- | --- |
| `README.md` | What the platform is, its toolkit, how its pages are written and checked, its status |
| `platform.md` | The conventions every page of the platform follows (shell and window, menus, dialogs, keyboard, copy casing, authentication, storage, packaging, accessibility), each with the reason |
| `commands.md` | Every command id of [commands.md](../commands.md) with this platform's placement, shortcut and notes (Windows also gives each shortcut a scope). One row per id; the checker verifies it |
| `index.md` | Every screen, flow and `messages` page of the spec, this platform's page for it, and its status |
| `screens/<id>.md`, `flows/<id>.md`, `messages.md` | One page per spec page. The same front matter for every platform: `id`, `title`, `spec`, `features`, `status`, optional `sources` and `screenshots` (Apple also `devices`) |
| `screenshots/<device>/<id>-<state>.png` | What the page looks like, by device folder; `<id>` is the page's id and `<state>` says what is shown (for example default, empty, error, locked, default-dark) |

A page never changes what the spec says. Behaviour, states, rules and copy keys come from the spec; a page adds presentation and implementation, and gives a reason for every difference. The sections a page must have, in order, are in [spec/README.md](../README.md) (Platform folders) and in the platform's own README. The checker (`python3 spec/tools/check-spec.py`) enforces front matter, sections, the index, command coverage and screenshot names, and that every listed screenshot exists.

## What goes in a page, whoever writes it

- **Name the control exactly**, in the platform's own terms, and say which element is the empty, loading, offline or error state.
- **List the source files** that implement the page (`sources:` in the front matter, repository paths), so a porter can read them. Prefer a short pointer to the file and the type over pasted code.
- **Say what is not obvious from the source**: why a control was chosen, what a platform quirk forced, what a porter must not simplify.
- **Link to the screenshots** the page lists, and say which state each shows.
- **Record differences** from the spec or from another platform under the page's "Different by design" (or, for Apple, "Differences between iPhone, iPad and Mac") with the reason. A difference without a reason is a bug in the page.
- **Never describe another platform from memory.** Read its page and its source; if neither says it, ask in [open-questions.md](../open-questions.md).

## Screenshots

Screenshots are regenerated by script, not captured or edited by hand, so that they can be refreshed after every UI change and always show the build they describe. A screenshot taken by hand goes stale unnoticed, differs in device, size, appearance and sample data, and cannot be reproduced by the next agent.

- **Tooling.** The existing capture tooling is the App Store harness in [design/app-store/](../../design/app-store/): `capture-ios.sh` and `capture-mac.sh` drive opt-in UI tests (`apps/apple/JournalScreenshots`) against a sample library seeded by `seed-library.sh`, with a fixed status bar and light and dark appearance. The script that captures the Apple screenshots, one per page state, is `design/spec-screenshots/capture.sh` ([README](../../design/spec-screenshots/README.md)); it builds on that harness with its own test classes. A page that has no screenshot, because its state cannot be captured, says so and why (Apple: "None" at the start of its Screenshots section).
- **One script per platform.** Each platform's capture script lives under `design/` and writes into that platform's `screenshots/<device>/` folder with the names above. A Windows script runs on Windows, an Android script on Android; an agent that cannot run a client does not add its screenshots.
- **Sample data only.** Capture from the seeded sample library, never from a personal library. Screenshots are public.
- **Size and format.** PNG, no alpha, one fixed size per device folder (recorded in the platform's README), light appearance by default and `-dark` for dark. Keep files small enough for a repository: crop to the window, not the desktop.
- **Referencing.** A page lists its screenshots under `screenshots:` in its front matter and links them in its Screenshots section. The checker warns about screenshots no page lists.

## Adding a platform (Android)

1. Create `spec/platforms/android/` with `README.md`, `platform.md`, `commands.md` and `index.md`, copying the Windows folder's shape: it is the model for a platform that follows the spec rather than being its first implementation. The `README.md` says what the toolkit is (for example Kotlin with Jetpack Compose and Material 3), the device folders for screenshots (for example `phone` and `tablet`), and the conventions that differ from the sentence-case and desktop assumptions of the Windows pages.
2. Add `android/AGENTS.md` for the app under `apps/android/` the way `apps/windows/AGENTS.md` does: goal, where to start, owner decisions already made, first milestone, how to document the implementation back here.
3. List every screen, flow and `messages` page in `index.md` with status `todo`, and write the pages in batches, each reviewed through the design gate in the root [AGENTS.md](../../AGENTS.md) before it is implemented.
4. Add `android` copy variants only through the owner-approved route in [spec/README.md](../README.md) (Copy keys); the `sentence` casing variant is shared with Windows.
5. Keep `parity.yaml` honest: `android` is `planned` until a feature ships, and a feature that originates on Android is added with `reference: android`.
6. Run `python3 spec/tools/check-spec.py`. It checks every folder named `apple`, `windows` or `android`; any platform other than Apple is checked the way the Windows folder is.
